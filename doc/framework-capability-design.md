# AstSight — 能力设计规格说明书（v2.16）

> **名称**：AstSight（AST + Sight）｜ **CLI**：`astsight` ｜ **Maven**：`io.astsight:astsight-core`
> **一句话主张**：上一代平台问「你测了多少条」，AstSight 只回答「这次变更带来什么质量结论」。
> **命名理由**：AST 是框架的地基——它靠代码图谱（tree-sitter 解析出的语法树）看清「改了什么」；Sight 是它的落点——再用契约与不变量说清「对不对」。**先看得见结构，才谈得上判定。**

| 项    | 内容                                                      |
| ---- | ------------------------------------------------------- |
| 定位   | 变更驱动 + 全量基线 + 历史回放的接口自动化测试引擎（运行模式三分，见 3.0）      |
| 形态   | CLI 直驱（无交互层、无意图层）                                       |
| 输入   | 需求文档、设计文档、代码库变更分支、数据库结构、接口契约（OpenAPI，可选）                |
| 输出   | 变更接口列表、接口画像、造数计划、业务用例集、pytest 用例代码、执行报告（含冲突检测/并行/重试/合并） |
| 文档性质 | **纯设计文档，不含实现**。所有 JSON 为数据契约，非代码                        |

> **⚠️ 已取代（2026-10-26）**：本文中的 **C1 规则库 / RuleSet / RuleBinding /
> RuleCoverage / A1.5 高风险规则确认** 已被实现层取代。当前流程是：
>
> ```
> 需求文档 + OpenAPI → cases prepare（context/prompt/schema）
>   → Skill/人工产出用例草案 → cases import（校验 + diff）
>   → 人工审核 → cases approve → 版本化 caseset.json
>   → run --mode cases → pytest → 报告
> ```
>
> 不再抽取中间规则层；人工审核对象从“规则”变成“可执行用例本身”。本文相关章节保留为
> 历史设计推演，与实现冲突时以 `engine/README.md` 和 `engine/astsight/cases/` 为准。

## 一、系统上下文

```
        ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
        │  需求/设计文档 │   │  Git 代码库  │   │  数据库      │
        └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
               │                 │                 │
               ▼                 ▼                 ▼
        ┌────────────────────────────────────────────────┐
        │               AstSight（本系统）               │
        │       感知层 → 分析层 → 生成层 → 执行层        │
        └───────────────┬────────────────────────────────┘
                        │
          ┌─────────────┼──────────────┐
          ▼             ▼              ▼
     用例资产库      CI 门禁        测试资产管理平台
    （pytest 代码） （通过率卡控）   （TestHub 等，旁挂对接）
```

**边界声明**：

- AstSight 是**引擎**，不是平台——不做用户管理、用例管理 UI、任务调度，这些交给 TestHub 类平台
- 与外部系统仅有三类交互：读（文档/代码/库结构）、写（用例代码与报告落盘）、执行（HTTP 请求被测服务 + SQL 造数）

## 二、总体架构

### 2.1 分层与能力映射

| 层   | 能力          | 职责一句话                          |
| --- | ----------- | ------------------------------ |
| 感知层 | C1 文档接入     | 需求+设计文档 → 规则库 `RuleSet`（资产定义见 **3.1**）             |
| 感知层 | C2 变更感知     | git 分支差异 → 变更接口列表（带置信度）        |
| 分析层 | C3 接口画像     | 单接口的完整档案：契约+约束+DB 映射+业务语义+下游依赖 |
| 分析层 | C3.5 下游依赖控制 | 对外调用的识别与 Mock（唯一主策略）+ 语义模型     |
| 分析层 | C5 数据准备     | 主表+关联表外键闭包 → 可执行的造数计划          |
| 生成层 | C4 用例设计     | **规则驱动**：画像+规则 → 用例集（正/负/边界三件套）          |
| 生成层 | C6 用例编码     | 用例集 → 可入库的 pytest 代码资产         |
| 执行层 | C7 执行验证     | 冲突检测 → 并行调度 → 执行 → 归因重试 → 报告合并；**判定依据取自规则 `expression`** |

### 2.2 主流程（数据视角）

```
需求/设计文档 ──C1──▶ 业务规则库 Rules
                          │
变更分支 ──────C2──▶ 变更接口列表 ChangedAPI[]
                          │
                          ▼
OpenAPI + DDL + Rules ──C3──▶ 接口画像 Profile[]（仅变更接口）
                          │
                          ▼
DDL + Profile ──────C5──▶ 造数计划 DataPlan[]
                          │
                          ▼
Profile + Rules + Plan ─C4──▶ 用例集 TestCase[]（含变更回归标记）
                          │
                          ▼
                     C6 ──▶ pytest 代码（tests/ 目录）
                          │
                          ▼
                     C7 ──▶ 执行报告 + 归因 + 门禁判定
```

**判定链（v2.15 补齐）**：`Rules` 不只流向 C3/C4（造题），**必须同时流向 C7（判卷）**——C7 判定时不读用例里的自由文本，只读规则的 `expression`。原流程缺这条边，等于规则只用来生成、不用来判定。

**设计约束**：各能力之间只通过**落盘的契约文件**通信（JSON），不共享内存对象——保证任一环节可独立重跑、可人工干预中间产物。

### 2.3 CodeGraph（代码图谱）的定位

> CodeGraph 不是某个能力，而是**贯穿感知层与分析层的基础设施**。它把代码解析为"符号 + 调用关系"图，提供两种追溯能力与一种 diff 能力，供多个能力模块复用。

**核心能力**：

| 能力          | 说明                 | 消费方                 |
| ----------- | ------------------ | ------------------- |
| **反向追溯**    | 谁调用了符号 A？（沿调用链向上）  | C2 变更感知             |
| **正向追溯**    | 符号 A 调用了谁？（沿调用链向下） | C3 下游识别、C3.5.1 语义反推 |
| **变更 diff** | 两个版本的符号级差异         | C2 变更感知             |

**在框架中的四种作用**：

| # | 作用         | 位置     | 追溯方向 | 具体用途                                                    |
| - | ---------- | ------ | ---- | ------------------------------------------------------- |
| 1 | 变更影响分析     | C2     | 反向   | 改 `calculate_total` → 追到 `POST /api/orders`，实现"改了什么测什么" |
| 2 | 下游依赖识别     | C3     | 正向   | 接口 → 服务 → 外部客户端，识别支付网关/MQ/Redis 等出站调用                   |
| 3 | Mock 语义完整性 | C3.5.1 | 正向   | 找出接口对下游响应的所有判断分支，反推必须 Mock 的语义集合                        |
| 4 | 调用参数溯源（辅助） | C3/C5  | 正向   | 入参经哪些转换写进哪张表（弱依赖，主靠 DDL+OpenAPI，图谱兜底）                   |

**CodeGraph 与接口依赖图谱的区别（两个不同的图，不可混淆）**：

| 维度 | CodeGraph（代码图谱） | 接口依赖图谱（业务级）                         |
| -- | --------------- | ----------------------------------- |
| 层次 | 实现级             | 业务级                                 |
| 节点 | 函数/类/模块         | 接口（`POST /api/orders`）              |
| 边  | 调用关系            | 数据依赖（A 产出 order_no → B 消费 order_no） |
| 回答 | 改了这个函数影响哪些接口    | 用例能不能串起来（登录→Token→下单）               |
| 来源 | 代码 AST 解析       | OpenAPI + 画像 produces/consumes      |

**关键设计决策**：

- CodeGraph 通过 **代码嵌入接入**（常驻 Node worker 进程内直接 `import` 其库 API，见 `CodeGraph-集成设计.md` v2.0）。**不走 MCP**：MCP 的返回面向模型阅读（源码/路径/爆炸半径混排的 markdown 包），不能作为结构化事实源，C2/C3/C5 需要机器可解析、可复现、可审计的输出。CLI 退为诊断工具（子命令覆盖面远小于库 API）
- 图谱由嵌入式 worker 现场构建或增量更新，构建结果落盘可复用；一仓一实例、一仓一写者
- 语言不支持的文件/符号**直接跳过**，标记 `unsupported`，不做降级兜底（宁可漏、不可错）
- **路由不能直接采信图谱输出**：实测 1.6.2 对 Flask `url_prefix` 与 Django `include()` 的前缀不拼接、对 `@app.get/@app.post` 完全不识别、对 Django 不产出 HTTP method。路由以**框架插件为主、图谱为辅**，两者交叉校验后才定证据等级（`CodeGraph-集成设计.md` 1.3/3.3）

**部署形态与侵入性（关键）**：

| 问题                   | 结论                            |
| -------------------- | ----------------------------- |
| 被测应用需要安装 CodeGraph 吗 | ❌ **不需要，零侵入**                 |
| 需要被测应用在运行吗           | ❌ 不需要，纯离线静态分析                 |
| 需要改被测应用配置/注入 SDK 吗   | ❌ 不需要                         |
| 需要什么                 | ✅ 仅需被测应用的**源码路径**（目录或 git 仓库） |

**原理**：CodeGraph 是**离线静态代码分析**，而非运行时埋点。它读取被测应用源码文件，用 AST 解析器构建符号与调用关系图——只读源码，不向被测应用注入任何东西。这与"链路追踪 agent / 插桩"这类运行时监控有本质区别。

**分析边界**：

| 可分析                 | 不可分析                         |
| ------------------- | ---------------------------- |
| 被测应用自有源码（路由/服务/调用点） | 三方依赖的二进制内部逻辑（import 的包看不到源码） |

> 不可分析三方依赖**不影响AstSight**——我们的追溯目标是"路由 → 自有服务层 → 外部客户端调用点"，这些调用点都在被测应用源码内，不在三方包内部。

**语言构建差异**：

- Python：直接读源码即建图（无编译步骤）
- Java/Spring：AST 可直接解析 `.java` 源码；若项目含运行时注解/反射动态路由，精度下降，需实测（见风险表"Java/Spring 路由识别精度不足"）

**开源引擎参照（复用而非重造）**：

> AstSight的 CodeGraph 底层**直接采用 `colbymchenry/codegraph`，不自研**。这里所称 **CodeGraph 特指 `colbymchenry/codegraph`** 这一个项目（Rust 内核 + tree-sitter + SQLite，提供 Node 库 API / CLI / MCP 三种形态，AstSight采用**库 API 嵌入**），它已提供AstSight C2/C3 所需的绝大部分底层能力。

| 引擎 | 仓库 | 技术栈 | 与AstSight能力的映射 |
|---|---|---|---|
| **CodeGraph**（主体参照） | github.com/colbymchenry/codegraph | Rust 内核 + tree-sitter + SQLite + **Node 库 API** | C2 变更感知（`getImpactRadius`/`getCallers`/`getCallees`）、符号调用图、**路由节点（仅供交叉校验，路径不可直接采信）** |

> 另有一个**独立项目**（非"CodeGraph"）`raghurammrsd/CODE_GRAPH_MCP`（Python AST + SQLite + MCP），其 **DB 血缘能力**（`READS_TABLE`/`WRITES_TABLE`/`MAPS_TO_TABLE`/`FOREIGN_KEY_TO`）是AstSight **C5 造数 DB 血缘**的能力参照来源——仅此一项，其余仍以 CodeGraph 为主。

**关键借鉴：证据等级（epistemic state）机制**——这是**设计理念的借鉴，不是对 CodeGraph 输出的读取**。实测 1.6.2 的库返回与 CLI `--json` **均不携带** `FACT`/`POSSIBLE`/`UNKNOWN` 字段，因此 AstSight 的 `verified`/`inferred`/`unmapped` 必须**自行判定**，由来源组合决定：

| 理念分级 | 含义 | AstSight 对应场景 | AstSight 判定依据 |
|---|---|---|---|
| 可证明事实 | AST 可证明 | 确定性提取的符号/调用/路由 | 单一确定性来源，或双源独立一致 |
| 推断未证实 | 推断但未证实 | 动态分发（`getattr`）、别名解析 | 仅单一来源（如图谱单方给出） |
| 无法判定 | 无法判定 | 反射、动态 SQL、重名符号未消歧 | 来源冲突且无法仲裁 → `unmapped` |
| 多源矛盾 | 多源矛盾 | OpenAPI 与 DDL 冲突 | 两路证据矛盾，保留双方证据不猜边 |

> AstSight 沿用这个理念：所有画像/血缘字段必须标注证据等级，**证据不足时显式标 `unknown` 而非猜测**——这是"事实源环节零 LLM"的底层保证。具体判定规则：**双源独立一致 → `verified`；单源 → `inferred`；冲突 → `unmapped`**（含"保留了冲突双方的证据"这一要求，不允许静默选边）。字段溯源仍保留 `constraint_source` / `inferred` / `unmapped` 三种口径。

**采用策略**：**只通过代码嵌入使用 CodeGraph，不自研 AST 图谱**（早期 tree-sitter 自研仅作可行性原型，非正式路径）。但**必须自研路由插件**——这不是可选项：实测 CodeGraph 的路由产出有四个静默缺陷（前缀丢失 ×2、method 缺失、节点数与清单不一致），直接采信会产出批量错误 URL，且错误不会以报错形式出现，只会表现为"测试失败但归因错"。是否可直接引用其调用图，仍须按语言/框架实测（见风险表）。

## 三、资产基线与能力规格（C1–C7）

> 先定义**资产**（3.1 规则库），再定义**能力**（C1–C7）。顺序不能反：规则库是唯一能被多个能力共同消费、且独立于用例存活的资产；能力只是往它里面写、从它里面取。
>
> 每项能力按统一模板：职责 / 输入 / 输出契约 / 核心逻辑（步骤级）/ 关键设计决策 / 异常与边界 / 门禁指标

### 3.0 运行模式（scope 三分）

触发方式会持续扩张（变更、定时、事件、流量），**因此框架不能以"变更驱动"命名，也不能只为变更设计**。三种模式共用同一条链路，差异只在"选哪个范围"：

| 模式 | 干什么 | 输入前提 | 何时用 | 核心约束 |
| -- | -- | -- | -- | -- |
| `full` | **建**基线：扫全量接口 → 画像 → 契约 → 生成 → 执行 | 代码库 + 文档即可，**不依赖 Git diff** | 首次接入、存量摸底、周期全回归 | **必须产出契约与画像基线**；只生成用例不建基线 = 负债 |
| `delta` | **维护**基线：只重判受影响范围 | 需要 Git 变更集 + 已有基线 | 每次提交、每次发布 | 未命中的接口**不得视为通过**，只能标注为未覆盖 |
| `replay` | **复用**基线：用今天的规则重判历史数据 / 影子流量 | 需要历史请求样本 + 已有契约 | 规则变更后回刷、事故回溯 | 结论必须携带**规则版本号**，否则跨版本不可比 |

**三条实现约束（不可妥协）**：

1. **三种模式不是三条 pipeline。** 画像、契约、生成、执行、判定五组组件完全共用，差异收敛为一个 `scope` 参数。若拆成两套代码，必然各自漂移——修一个 bug 要改两遍。
2. **CLI 契约统一**：`astsight run --mode full|delta|replay --project <id>`。模式是参数，不是子命令分支。
3. **三种模式都必须输出覆盖边界**：`unmapped`（没看到 / 没判到）必须单列进报告。**静默通过是最大风险**——尤其是 `full` 模式扫出的"我以为我全测了"。

> 门禁口径随之收紧：C2 的「召回 ≥90%」只对 `verified` 路由成立，`unmapped` 必须独立计数并阻断放行，不得并入通过率分母。

### 3.1 规则库（Rule Base）——唯一的判定资产

> **规则库不是 C1 的中间产物，是平台的一等资产。** C1 往里写，C4 从里取用例，C7 拿它当裁判——三者共用同一份，不得各自复制。

**为什么必须独立于用例存放**：

| 维度 | 断言写在用例里 | 断言来自规则库 |
| --- | --- | --- |
| 一条规则的存在份数 | = 用例数（200 条用例就是 200 份） | 1 |
| 规则变更时的影响面 | 靠人回忆 | 反查 `RuleBinding` 精确得出 |
| 能否用今天的规则重判历史数据 | 不能（历史用例已固化） | 能（`replay` 模式的前提） |
| 失败归因成本 | N 条用例 = N 个独立失败 | 1 条规则被违反 N 次，一次归因 |
| 生成阶段的覆盖判据 | 无（只能数用例条数） | 规则-用例矩阵，缺口可见 |

一句判据：**删掉所有用例，规则还在 → 合格；规则随用例一起消失 → 不合格。**

#### 3.1.1 权威等级（决定它能不能当 oracle）

规则按来源分四级，**等级决定它有没有资格参与判定**：

| 等级 | 来源 | 可否作 oracle | 典型形态 |
| --- | --- | --- | --- |
| **A** | 需求/设计文档的显式约束（含字段定义表、错误码表） | **可以**，可当一票否决 | 「库存不足返回 40001」「退款不超原单实付」 |
| **B** | 需求文档的流程/业务描述（需推断） | **可以**，但必须人工确认 | 「优惠券可叠加，但同类券互斥」 |
| **C** | **从代码反推**（读实现得出"期望"） | **禁止单独作 oracle** | 「现在这么算，所以期望这么算」 |
| **D** | 历史缺陷 / 线上事故归纳 | **条件可用**：作回归断言，须标 provenance | 「曾超卖，故补并发不变量」 |

**C 级为什么禁止**：它就是自证陷阱的工业化形态。代码反推的"期望"与缺陷同源，**它能保证的只有"行为没变"，不能保证"行为正确"**。

工程上 C 级不是不能用，而是只能当**差分 oracle** 用——新旧系统同一输入结果一致即通过，必须显式标 `oracle_kind=differential`，且不得计入"业务正确性"的统计口径。

这条与 C2 的 `verified/inferred/unmapped` 是同一套哲学：**不可信的东西不能算进"通过"。**

**未标等级 = 按 C 级处理**（安全失败，不臆造）。

#### 3.1.2 生命周期

| 状态 | 含义 | 允许转移 |
| --- | --- | --- |
| `candidate` | 抽取产出，未经确认 | → `confirmed` / `rejected` |
| `confirmed` | 人工确认，可进下游 | → `active` |
| `active` | 在用，参与生成与判定 | → `deprecated` / `superseded` / `conflicted` |
| `superseded` | 被新版本替代（保留，`replay` 需要） | 终态 |
| `deprecated` | 业务下线导致失效 | 终态 |
| `conflicted` | 与另一条规则冲突未裁决 | → `confirmed`（裁决后） |

**只有 `confirmed`/`active` 参与用例生成；只有 `active` 参与判定。** `candidate` 永不静默生效——高风险必确认、低风险 `auto` 放行（沿用 A1.5 口径）。

**规则体检**（每轮 `full` 跑一次），四类病灶：

| 病灶 | 判据 | 处置 |
| --- | --- | --- |
| 空转 | 连续 N 轮（默认 3）无任何用例绑定 | 提示补用例或降级 |
| **永真** | 绑定用例全通过，且从未在任何变异/缺陷中触发 | 提示"这条规则可能在守护空气" |
| 失配 | 规则文本已改但 `RuleBinding` 未更新 | 阻断，要求重跑 C4 |
| 悬空 | 规则引用的字段/实体在画像里不存在 | 阻断，规则与实现已脱节 |

第二条「永真」最值得警惕：**一条永远通过的规则，和一条不存在的规则，在报告上长得一模一样。**

#### 3.1.3 数据模型

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `RuleSet` | id, project, doc_versions[], version, status, generated_at | 一次抽取的产物快照，固化全部源文档版本 |
| `Rule` | 见下方 JSON | 单条规则（C1 契约 + 4 个治理字段） |
| `RuleBinding` | rule_id, target_type, target_ref, strength, evidence | 规则 ↔ 接口/字段/表的绑定，**是覆盖率的分母来源** |
| `RuleCoverage` | rule_id, case_ids[], coverage_kind, assert_strength, last_judged_at | 规则 ↔ 用例的覆盖矩阵 |

`Rule` 在 C1 契约之上补 5 个治理字段（其余不变）：

```json
{
  "authority": "A | B | C | D（未标按 C 处理）",
  "status": "candidate | confirmed | active | superseded | deprecated | conflicted",
  "expression": "stock >= qty（可执行判定式；为空 = 只能指导生成，不能参与判定）",
  "oracle_kind": "invariant | exact | relation | differential | none",
  "version": 3
}
```

**`expression` 为空是一个必须显式存在的状态**，否则"我有 200 条规则"和"我有 200 条能判的规则"会被混为一谈。

#### 3.1.4 抽取策略（双源分工）

| 源 | 优先取什么 | 抽取方式 | 产出等级 |
| --- | --- | --- | --- |
| 技术文档（接口设计 / 表设计） | 字段类型、长度、枚举、必填、唯一、外键、错误码 | 表格结构化解析（确定性，零 LLM） | A |
| 需求文档 | 业务流程、状态机、金额与优惠、权限、时效 | 关键词命中 + 复杂段落交 LLM 精读 | A/B |
| `acceptance_criteria`（验收标准字段） | 最接近可执行判定的材料 | 直接映射为 `expression` 候选 | A |

**冲突裁决**：技术文档 > 需求文档（实现约束更严）；同字段冲突**不自动合并**，落 conflict 清单交人工。宁可少一条，不可错一条——一条错规则会污染它绑定的全部用例。

**抽不出来的三类（必须显式记录，不能假装没有）**：

1. **隐含规则**——没人写下来的行业惯例（如"退款不能超原单"）。
2. **数量级规则**——"高并发下不超卖"需要并发语义，文本里只有形容词。
3. **跨系统规则**——对账、上下游一致性，单份文档看不全。

这三类决定了规则库永远有一部分 `unmapped`。**报告必须报出"本次有 X 条规则缺失，涉及 Y 个接口"**，不得静默略过。

#### 3.1.5 规则驱动的用例设计（C4 改造）

覆盖矩阵是生成主线，不再是"想到什么写什么"。每条 `active` 规则生成**三件套**，缺一不可：

| 形态 | 要求 | 例（库存规则） |
| --- | --- | --- |
| 正例 | 规则被满足 | 库存 5 买 1 → 成功 |
| **负例** | 规则被违反，断言必须精确命中错误码/错误字段 | 库存 1 买 2 → 40001 |
| 边界 | 表达式两侧临界值（±1） | 库存 2 买 2 → 成功；买 3 → 失败 |

**覆盖率的正确算法**：

```
规则覆盖率 = 已绑定 ≥1 用例（且含负例）的 active 规则数 ÷ active 规则总数
```

分母是**规则**，不是用例。这是它与传统覆盖率最本质的区别：**用例再多也补不上一条缺失的规则。**

**`expression` 为空的规则**：仍生成用例，但断言降级为"人工核对清单"，报告单列 `manual_required`，**不计入覆盖率分子**。

#### 3.1.6 断言强度与保真校验

C6 必须为每条断言标注强度档：

| 档 | 形态 | 例 | 能抓到什么 |
| --- | --- | --- | --- |
| L1 | 状态码 / 字段存在 | `status==200`、`data.id != null` | 崩溃、契约破坏 |
| L2 | 确定值 | `total == 108.00` | 计算错误（数据一变就误报） |
| L3 | 关系式 | `refund <= order.paid` | 计算口径错误 |
| **L4** | **跨实体不变量** | 余额=流水和、库存≥0、状态机合法 | 资损、状态错乱 |

**保真校验规则**：规则表达式落在 L3/L4，而 C6 生成的断言只有 L1/L2 → **必须报警为"翻译降级"**。这是"业务用例写得很好、脚本其实什么都没验"的唯一自动检测手段——自然语言期望翻译成断言表达式，语义只减不增。

**断言有效性用变异测试度量**（挂在 `delta` 上，成本可控）：

- 只对本次变更改动的代码行造变异（边界反转 / 常数改错 / 校验删除 / 分支短路），约 5~15 个
- 只跑覆盖这些行的用例（约占全量 5%）
- **变异存活率 0% 才可放行**；存活的变异逐条列出，即"本次改动的断言盲区"

它比覆盖率准确得多：覆盖率说"这行被执行过"，变异存活率说"这行改错了会不会被发现"。

#### 3.1.7 门禁

| 指标 | 阈值 | 说明 |
| --- | --- | --- |
| 规则抽取准确率 | 100%（确定性表格部分） | 人工标注对照 |
| 高风险规则确认率 | 100% | P0/高风险未确认即阻断（沿用 A1.5） |
| 规则覆盖率 | ≥80% | 分母 = `active` 规则数，分子须含负例 |
| 断言保真率 | 无 L3/L4 → L1/L2 降级 | 降级逐条列出 |
| 变异存活率（delta） | 0% | 存活即阻断放行 |
| 空转 + 永真规则占比 | ≤10% | 超阈值要求清理，否则规则库虚胖 |

### C1 文档接入

| 项  | 内容                                        |
| -- | ----------------------------------------- |
| 职责 | 将需求文档与设计文档解析为结构化的字段级业务规则                  |
| 输入 | 需求文档（md/docx/pdf）、设计文档（含接口设计、表设计章节）、文档版本号 |
| 输出 | `RuleSet`（落盘 `ruleset.json`）：规则集合 + 源文档版本快照；字段与生命周期见 **3.1.3** |

**规则数据契约**：

```json
{
  "id": "BR-01",
  "text": "创建订单时若商品库存不足，应返回 40001",
  "type": "field_constraint | process | performance | permission",
  "entities": ["订单", "库存"],
  "fields": ["stock", "qty"],
  "source": {"doc": "requirement.md", "version": "v1.3", "section": "3.2"},
  "priority": "P0",
  "reasoning": "依据 requirement.md 第 3.2 节「库存校验」的「库存不足返回 40001」推断（仅 P0/高风险规则留痕）",
  "confirm": {"status": "confirmed | rejected | deferred | auto", "by": "人工", "at": "..."}
}
```

> `reasoning` 与 `confirm` 由下游环节追加：`reasoning` 是 A1 对 P0/高风险规则的推理留痕（供人工确认审阅，不进下游）；`confirm` 是 A1.5 人工确认环节回写的状态（见 `agent-architecture.md` A1.5 章节）。A1 本身产出 `id~priority` 七字段，后两字段是链路上游的增强。

**核心逻辑**：

1. 文档切块（按标题层级），识别章节类型（业务流程/字段定义/非功能要求）
2. 表格型内容（设计文档的字段定义表）结构化提取：字段名/类型/约束/说明
3. 文本型内容规则提取：命中约束关键词（必须/不得/超过/≤/唯一…）的语句候选
4. 复杂语义段落（条件嵌套、流程分支）交 LLM 精读，输出同契约
5. 规则冲突裁决：**设计文档 > 需求文档**；同字段冲突记录 conflict 标记，不静默覆盖
6. **权威等级判定**（见 3.1.1）：按来源打 A/B/C/D，代码反推得到的一律 C 级
7. **`expression` 试译**：能翻译成可执行式的填 `expression`，翻不出来的留空并标 `oracle_kind=none`——两类规则必须可区分，不得用自然语言冒充可执行判定
8. 落 `RuleSet` 快照（含全部源文档版本），状态初始为 `candidate`

**关键设计决策**：

- 冲突不自动合并，输出冲突清单供人工裁决——规则错误会污染下游所有用例
- 文档带版本，版本间 diff 出"规则增/改/删"，作为增量回归的输入之一
- **抽取目标不是"规则越多越好"，而是"能判的规则越多越好"**：报告须同时给出三个数——规则总数、有 `expression` 的数、覆盖到的接口数。只报第一个数是自嗨
- 抽不出的规则要显式记入 `unmapped` 清单（隐含规则/数量级规则/跨系统规则，见 3.1.4），不得静默丢弃

**异常与边界**：扫描件 PDF 不支持（前置要求可提取文本）；无编号文档自动编号并在报告中注明

**门禁**：见 **3.1.7**。C1 自身只负责"字段约束提取准确率 100%（确定性部分）"与"入库前过人工确认门"（高风险必确认、低风险 auto 放行，见 `agent-architecture.md` A1.5 章节）

### C2 变更感知

| 项  | 内容                                 |
| -- | ---------------------------------- |
| 职责 | 从代码库变更分支精确推导受影响的接口列表               |
| 输入 | 仓库路径、base 分支、target 分支、代码图谱（可现场构建） |
| 输出 | `changed_apis.json`：变更接口列表         |

**数据契约**：

```json
{
  "method": "POST", "path": "/api/orders",
  "handler": "order_service.create_order",
  "confidence": "high | medium | low",
  "changed_symbols": ["create_order", "calculate_total"],
  "change_files": ["services/order_service.py"],
  "trace": "calculate_total ← create_order ← POST /api/orders"
}
```

**核心逻辑**：

1. `git diff base..target` 取变更文件与函数级变更符号（AST diff）
2. 代码图谱沿调用链**反向追溯**至路由层（追溯深度可配，默认 5）
3. 路由注册表匹配框架路由（框架插件化：FastAPI/Flask/Django/Spring）
4. 置信度判定：
   - 高：变更符号即路由处理函数，或路由函数体直接改动
   - 中：路由调用的服务/数据访问层变更
   - 低：仅配置、工具类、或被多个路由共享的公共函数变更
5. 语言不支持 → 该变更符号标记 `unsupported`，从变更集剔除，报告显式列出（不降级兜底）

**实现进展（2026-10-27，以 `engine/` 为准）**：

- 第 1 步已扩展为「Python AST + CodeGraph 文件符号表」：非 Python 文件用
  `getNodesInFile` 的 `startLine/endLine` 做行区间相交，框架内不另写 Java 解析器；
- 第 2 步把 CodeGraph 节点 id 传给 `impact(node_id=...)`，避免 Java 同名重载合并；
- 第 3 步的 Spring 路由由 CodeGraph 原生 Java resolver 提供；AstSight 尚未实现
  Spring 路由插件第二来源，因此 Spring 路由证据为 `inferred`；
- 类级/文件级/纯删除变更按 API 级兜底并标 `inferred`，不假装方法级精度；
- **未完成**：`low` 置信度隔离、20 个真实分支的召回率/误报率基准、Spring
  真实仓库路由覆盖分母。

**关键设计决策**：

- **低置信度不进入自动用例生成**，只在报告列出供人工勾选——噪音隔离
- `trace` 字段必须保留完整追溯链，供人工判断影响真实性
- Java/Spring 路由识别精度仍是已知风险：CodeGraph 1.6.2 的类级 `@RequestMapping`
  拼接已在合成项目验证，但 Spring 路由只有单源（无 AstSight 插件交叉校验），
  真实仓库覆盖率仍需按 20 个变更分支做基准后再定全量启用

**异常与边界**：分支不存在/无差异 → 明确报错退出；rename/移动文件按内容相似度归并

**门禁**：变更接口召回率 ≥90%、误报率 ≤30%（人工标注 20 个真实变更分支验证）

### C3 接口画像

| 项  | 内容                                              |
| -- | ----------------------------------------------- |
| 职责 | 为每个变更接口建立唯一事实源档案                                |
| 输入 | ChangedAPI[]、OpenAPI（可选）、DDL/库直连、rules.json、术语表 |
| 输出 | `api_profiles.json`                             |

**画像数据契约**：

```json
{
  "endpoint": "POST /api/orders",
  "params": [{
    "name": "qty", "in": "body", "type": "integer", "required": true,
    "constraints": {"min": 1, "max": 999},
    "constraint_source": "design_doc",
    "db_mapping": {"table": "orders", "column": "qty", "db_type": "int(11)"},
    "biz_meaning": "购买数量",
    "rules": ["BR-01"]
  }],
  "responses": {"200": {"fields": ["order_no", "status"]}},
  "dependencies": {"produces": ["order_no"], "consumes": ["sku_id"]},
  "downstream_deps": [{
    "id": "pay-gateway",
    "type": "sync_rest | mq | cache | rpc | third_party_api | storage",
    "target": "POST https://pay.internal/gateway",
    "trigger": "支付提交时",
    "side_effect": {"has": true, "desc": "真实扣款"},
    "control": "mock",
    "mock_response": {"success": true, "trans_no": "T{case_id}_PAY"}
  }],
  "conflicts": [{"field": "qty", "openapi": "无上限", "design": "≤999", "resolved": 999}]
}
```

**核心逻辑**：

1. 契约提取：OpenAPI 优先；缺失时从代码 AST 提取（框架插件）
2. DB 映射：字段名匹配 + 命名约定（驼峰/下划线归一）+ 设计文档表映射章节
3. 三路约束校验：OpenAPI / DB DDL / 文档规则，**取最严**，全部冲突记入 conflicts
4. 依赖标注：写操作响应中的业务标识（`*_no`、`*_id`、`*_code`）标为 produces；入参中引用外部标识的标为 consumes
5. **下游依赖识别**：从代码图谱沿调用链**正向追溯**（路由→服务→外部客户端），识别 HTTP 客户端、MQ 生产者、Redis/缓存、RPC、第三方 SDK 的调用点，标注类型（副作用判定已降级为可选的安全护栏标记，见下文）
6. **DB 读写血缘**：从代码图谱沿调用链正向追溯，识别接口对数据库的读/写访问，产出"接口→服务→ORM/SQL→表→列"的血缘链（详见下方"DB 读写血缘"）
7. 业务语义附着：术语表 + 规则命中 + DB comment

**DB 读写血缘（接口对数据库的访问关系，C5 造数的前置输入）**：

> 画像不仅要知道"下游有哪些外部服务"，还要知道"这个接口读了/写了哪些表、哪些列"——这是 C5 造数（`fk_links` 闭包、拓扑排序）的准确依据。本能力由代码图谱正向追溯 + DDL 匹配确定性完成，零 LLM。

| 血缘边 | 含义 | 来源 | 证据等级 |
|---|---|---|---|
| `READS_TABLE` / `READS_COLUMN` | 接口路径上的 SELECT 访问 | AST 提取 SQL/ORM 读 | `verified` |
| `WRITES_TABLE` / `WRITES_COLUMN` | 接口路径上的 INSERT/UPDATE/DELETE/`.add()`/`.save()` | AST 提取 SQL/ORM 写 | `verified` |
| `MAPS_TO_TABLE` / `MAPS_TO_COLUMN` | ORM 模型字段 → 物理表列 | 框架模型映射（SQLAlchemy/Django ORM 等） | `verified` |
| `FOREIGN_KEY_TO` | 表间外键关系 | DDL 解析 | `verified` |

**血缘链示例**（与下游依赖识别同向，供 C5 直接消费）：

```
POST /orders → OrderService.create_order → OrderRepository.insert_order
  → WRITES_TABLE: orders
  → FOREIGN_KEY_TO: orders.user_id → users.id
  → FOREIGN_KEY_TO: orders.sku_id  → products.sku_id
```

**关键设计决策（血缘）**：

- 血缘是 C5 造数的**事实源输入**：C5 的 `fk_links` 直接由 `FOREIGN_KEY_TO` 生成，不再依赖字段名启发式
- **证据分级**：ORM/SQL 能静态证明的标 `verified`；动态 SQL（字符串拼接、`getattr` 表名）标 `inferred`，推不出的标 `unmapped`——**不猜测**
- 与 C2/C3 下游识别共用同一条正向追溯链路，不重复建图

**证据等级（全局口径，对齐 CodeGraph 诚实标记）**：

| 等级 | 含义 | 示例 |
|---|---|---|
| `verified` | AST/DDL 静态可证明 | 直接 ORM 调用、字面量 SQL |
| `inferred` | 推断但未证实 | 命名约定补推、动态 SQL |
| `unmapped` | 无法判定 | 反射、逻辑外键缺失 |

> 全框架所有画像/血缘字段统一采用三级证据等级，取代分散的 `constraint_source`/`inferred`/`unmapped` 混杂表达；`conflicts` 仍独立记录多源矛盾。

**术语定义：副作用（side_effect）——安全护栏标记，非策略选择依据**：

> AstSight采用**全 Mock**（读写下、有副作用与否，一律 Mock，不透传），因此"副作用"不再用于决定"要不要 Mock"。它退化为**安全护栏**：防止 Mock 配置错误或注入失效导致真实出站请求漏出。

**降级后的定位**：

| 原用途（已废弃） | 新用途（保留） |
|---|---|
| 决定下游"要不要 Mock" | ❌ 不需要了——全 Mock，读/写都 Mock |
| 决定 Mock 安全等级 | ❌ 不需要了——无透传场景 |
| **透传熔断告警** | ✅ 保留——若 `side_effect.has=true` 的下游出现真实出站请求，立即熔断并告警 |

**字段语义（收敛后）**：

| side_effect.has | 含义 | 作用 |
|---|---|---|
| `true` | 该下游有真实业务影响（扣款/发消息等） | 作为**熔断护栏**：出现真实透传立即阻断 |
| `false` | 只读/无业务影响 | 无额外护栏（仍 Mock，但漏出危害小） |

**关键结论**：

1. **C3 下游识别不再需要精确判定"读/写"**——只需"识别出所有下游"这一个动作，副作用判定从"必须"降为"可选增强"
2. **`side_effect` 字段保留但语义改变**：从"策略选择输入"变为"安全护栏标记"，服务于"透传熔断"而非"Mock 决策"
3. **熔断逻辑**：执行层（C7）在运行时监控，若任何下游出现真实出站请求（Mock 注入失效），立即阻断执行并告警——`side_effect.has=true` 的下游熔断优先级最高（资损红线）

> 这符合测试领域的一贯原则：**资损防控的护栏不因"正常流程不需要"而省略**。全 Mock 是正常态，但护栏要防的是异常态。

**字段口径**：`side_effect.has` 为布尔（`true`=有真实业务影响），`desc` 为人工可读说明。因已降级为护栏标记，判定精度要求降低——仅需标出"高危写操作"（扣款/发消息/发货等资损类），其余可标 `false` 或省略；无法判定的标 `unknown` 亦不影响主流程。

**关键设计决策**：

- 画像聚合器是**纯确定性逻辑，不放 LLM**——它是下游一切的事实源，错一处全盘错
- 术语表是独立资产文件，可持续积累，跨项目复用
- 下游依赖识别与 C2 的变更追溯**方向相反**：C2 是"谁影响这个接口"（反向），这里是"这个接口影响谁"（正向）

**异常与边界**：字段无法映射 DB 时标记 `unmapped` 而非猜测；无 OpenAPI 且 CodeGraph 不支持该框架时标记 `contract_incomplete` 并显式告警（不降级兜底）

**门禁**：字段约束提取准确率 100%；映射冲突检出率 = 人工基准；下游依赖识别召回率 ≥85%（对照人工梳理的调用清单）

### C3.5 下游依赖控制策略

> 被测接口内部的对外调用（下游依赖）是接口测试最易失真的环节。**AstSight的测试数据由数据库直插构造，上下游并未打通**——下游服务里不存在与我们造数匹配的业务上下文（账号、余额、订单状态等），因此连下游和放行都不可行，**Mock 是唯一主策略**。

**核心结论：Mock 唯一主策略**

| 策略              | AstSight适用性      | 原因                                          |
| --------------- | ----------- | ------------------------------------------- |
| **Mock（打桩）**    | ✅ **唯一主策略** | 出站请求处截断，注入编排好的响应，根本不触达下游，规避"下游查无数据"与"真实副作用污染" |
| Passthrough（透传） | ❌ 不可用       | 下游无对应业务数据 → 假红；有副作用 → 污染真实环境（全 Mock 已杜绝透传）                |
| Sandbox（测试替身）   | ⚠️ 暂不启用     | 假下游同样需要匹配我们的造数，数据对不上；需额外维护替身服务              |
| Contract（契约校验）  | ⚠️ 暂不启用     | 仅作为将来打通上下游后的可选项，当前不做                        |

**Mock 分级（按依赖类型，全部落在 Mock 内）**：

| 下游类型            | Mock 方式                       | 断言重点                 |
| --------------- | ----------------------------- | -------------------- |
| sync_rest / rpc | 出站 HTTP 拦截，注入响应（成功/超时/降级/异常码） | 我方调用参数 + 响应处理结果      |
| mq（消息队列）        | 生产者消息拦截，断言消息内容                | 消息是否发出、内容是否正确        |
| cache（Redis 等）  | 测试实例 or 出站拦截                  | 缓存读写行为（可用测试实例，非下游服务） |
| third_party_api | 出站拦截，注入编排响应                   | 调用参数 + 降级/重试处理       |
| storage（对象存储）   | 出站拦截，注入成功/失败响应                | 上传/下载调用正确性           |

**核心机制**：

1. **注入点**：Mock 发生在"被测服务的出站请求"处，通过以下方式之一实现——
   - HTTP 代理层拦截（对 REST 下游最通用，改 host 指向 mock 服务）
   - SDK 注入点 / 依赖注入（框架原生支持时最干净）
   - MQ 消费端不启动、生产者指向测试 topic
2. **响应编排**：Mock 响应按用例编排（成功/超时/降级/异常码），响应体用数据契约变量（`T{case_id}_PAY`）保证用例间隔离
3. **调用断言**：Mock 记录"是否被调用、调用几次、请求参数"，供用例断言（如"取消订单后必须发送退款消息"）
4. **Mock 数据与 DB 造数对齐**：Mock 响应中的业务标识（如 `trans_no`）若需回写被测库，须与 DB 造数计划共享同一变量域（`T{case_id}_` 前缀），保证"我方 DB 状态 ↔ Mock 返回"逻辑自洽
5. **透传熔断护栏**：执行层监控所有出站请求——若任何下游出现真实透传（Mock 注入失效/配置遗漏），立即阻断执行并告警；`side_effect.has=true` 的下游（资损类）熔断优先级最高


**关键设计决策**：

- **Mock 覆盖全部下游依赖，无一透传**——这是AstSight的前提约束（数据未打通），不是可选优化
- **MQ 类依赖的断言在"消息内容"而非"下游结果"**——消息是否发出、内容是否正确由 Mock 断言，下游消费结果不属于本接口职责范围
- **Mock 响应与 DB 造数共享变量域**——两者必须对齐，否则会出现"Mock 返回的流水号落不了库"这类割裂
- Mock 响应和调用断言都是确定性编排，不放 LLM
- Cache（Redis）属特例：可用独立测试实例而非 Mock，因为它不是"未打通的下游服务"，而是可随测随建的基础设施

**异常与边界**：下游依赖无法识别（动态调用、反射、配置化 URL）→ 标记 `unidentified` 并在报告告警，交由人工补画像；全 Mock 原则下不存在"透传放行"的正常例外——任何真实出站请求都触发熔断告警（唯一例外：Cache/Redis 等可随测随建的基础设施，不作为"下游服务"处理）

**门禁**：全部下游依赖 Mock 覆盖率 100%（每个 downstream_dep 必有 Mock 编排）；存在未 Mock 且未显式声明的下游 → 阻断执行

#### C3.5.1 Mock 语义模型（Mock 响应如何符合用例需求）

> Mock 不是"随便返回一个 200"——Mock 响应必须承载正确的业务语义，否则测出的结果是假的。本节定义 Mock 语义的**三层来源**与**确定性生成规则**。

**问题本质**：Mock = 一个"假的下游"，其行为必须真实可信。语义错了会导致两种失真——① 被测接口对错误语义的响应"正确处理"→ 假绿（没测到真实逻辑）；② 被测接口走了不该走的分支 → 断言失真。

**Mock 语义三层来源**：

| 层        | 来源              | 决定什么                         | 缺失后果             |
| -------- | --------------- | ---------------------------- | ---------------- |
| 契约层（形）   | 下游 OpenAPI/接口文档 | 响应**骨架**：字段、类型、枚举、错误码结构      | Mock 字段对不上 → 跑不通 |
| 业务知识层（神） | 需求/设计文档 + 术语表   | **什么条件返回什么**：成功/余额不足/超时等语义分支 | 语义瞎编 → 假绿        |
| 用例意图层（选） | 测试用例要验证什么       | 本次执行**返回哪个语义**               | 语义与用例错位 → 断言失真   |

**关键：三层缺一不可**。契约定"形"、业务知识定"神"、用例意图定"选"。

**Mock 语义模板（资产，可复用）**：

每个下游依赖维护一份语义模板，枚举其所有业务分支：

```json
{
  "dep_id": "pay-gateway",
  "semantic_branches": [
    {"name": "success",  "condition": "账户余额充足且请求合法",
     "response": {"code": 200, "trans_no": "T{case_id}_PAY", "status": "paid"}},
    {"name": "insufficient_balance", "condition": "余额不足",
     "response": {"code": 40001, "message": "余额不足"}},
    {"name": "timeout", "condition": "下游超时（网络抖动）",
     "response": {"timeout": true}},
    {"name": "degraded", "condition": "下游降级",
     "response": {"code": 503, "message": "服务降级"}}
  ]
}
```

**语义模板的推导规则（确定性）**：

1. **契约层**：从下游 OpenAPI/接口文档提取响应 schema → 填充每个分支的 response 骨架
2. **业务知识层**：从需求/设计文档提取该下游的**业务分支规则**（"余额不足返回 40001"这类），映射为 condition + response
3. **语义覆盖完整性校验**：模板必须覆盖被测接口**可能消费到的所有分支**——从被测接口代码的正向追溯中，找出它对下游响应做的所有判断（如 `if resp.code == 40001`），反推出必须 Mock 的分支集合。**漏一个分支，就有一条被测代码路径永远测不到**

**用例 → 语义分支绑定**：

每个用例在生成时**显式声明**它要驱动哪个语义分支：

```json
{
  "case_id": "TC-B-004",
  "dep_mock": [{"dep_id": "pay-gateway", "branch": "insufficient_balance"}]
}
```

- 正向用例绑定 `success`，负向/降级用例绑定对应异常分支
- 无绑定的下游 → 默认 `success`（并在报告标注"未显式绑定，采用默认语义"）
- **一条用例可绑定多个下游的不同分支**（下单接口同时 Mock 支付 + 库存两个下游）

**关键设计决策**：

- **语义模板是资产不是一次性配置**——它随下游契约/业务规则演化，需与下游接口文档同步维护（类似术语表）
- **语义分支完整性由"被测接口消费面"反推校验**——这是防止"漏测分支"的唯一可靠手段，比人工枚举更准
- **用例显式绑定语义分支**——禁止"默认返回一个笼统成功"，因为未绑定的语义分支是测试盲区
- Mock 语义推导的**契约层和业务知识层**是确定性提取（文档解析），**语义理解中的复杂分支条件**可用 LLM 辅助提取但需人工复核（此处 LLM 属 C1 文档接入范畴，非运行时）

**异常与边界**：下游无接口文档 → 语义模板无法建形，降级为"从被测接口的消费面反推最小语义集合"（只保证跑通，不保证语义准确，标记 `semantic_inferred`）；被测接口对下游响应存在无法静态识别的判断（动态分支）→ 该下游标记 `semantic_incomplete`，报告提示人工补全

**门禁**：每个下游的语义模板覆盖被测接口全部消费分支（覆盖率 100%）；每条用例显式绑定语义分支（默认成功也须显式声明）

#### C3.5.2 下游信息获取（要不要下游 git）

> Mock 需要下游的"契约 + 业务语义"，不是"实现"。按信息充分度分三档，决定是否需要下游源码。

**信息充分度三档**：

| 档位                  | 需要的输入                         | 能 Mock 到的程度                             |
| ------------------- | ----------------------------- | --------------------------------------- |
| **档 1：只读下游文档**      | 下游 OpenAPI/接口文档（swagger、wiki） | 契约层✅（响应骨架/字段/错误码）；业务语义层⚠️（靠文档描述推断，可能不全） |
| **档 2：加下游 git（只读）** | 下游源码（零侵入静态分析）                 | 契约层✅ + 业务语义层✅（从代码逻辑精确提取"什么条件返回什么"）      |
| **档 3：运行时观测**       | 下游运行环境/流量录制                   | 语义层最准，但成本与侵入性最高，**AstSight不依赖**              |

**关键判断：何时必须给下游 git**：

- 下游 OpenAPI 文档写清了**错误码 + 触发条件**（如"40001 = 余额不足"）→ **档 1 足够，不需 git**
- 下游文档只有字段结构、**没有语义规则**（多数内部服务 swagger 只列 response schema）→ 业务语义层缺失，**需下游 git**，用 CodeGraph 静态分析下游代码，从其判断逻辑反推语义分支

**核心结论**：

1. **下游 git 不是"必须依赖"，是"语义精确度的增益"**——能拿到文档就先用文档，语义不全再补源码
2. **即便给下游 git，也是只读静态分析、零侵入**——与被测应用共用同一套 CodeGraph，下游无需安装任何东西、无需运行
3. **下游信息获取是"渐进增强"的**：档 1 先行（跑通），档 2 补语义（跑准），避免一开始就被"要下游代码"卡住落地

**信息缺口标记**：下游语义分支无法从文档或源码获取时，标记 `semantic_inferred`（仅保证跑通）或 `semantic_incomplete`（人工补全），并明确记录"该下游的 Mock 语义未经精确验证"——**不允许在报告里假装语义完整**。

**门禁**：每个下游至少达到档 1（有契约骨架）；业务语义层缺失的下游必须显式标记缺口，不得静默

### C5 数据准备

| 项  | 内容                                            |
| -- | --------------------------------------------- |
| 职责 | 生成主表+关联表的完整造数计划，保证业务链上数据状态正确                  |
| 输入 | DDL/库结构、api_profiles.json、rules.json、种子数据（可选） |
| 输出 | `data_plan.json`                              |

**数据契约**：

```json
{
  "case_id": "TC-B-001",
  "tables_order": ["users", "products", "orders"],
  "target_state": "存在未支付订单，库存充足",
  "fixtures": {
    "users":    [{"username": "T{case_id}_u1", "status": 1}],
    "products": [{"sku_id": "T{case_id}_S1", "stock": 100}],
    "orders":   [{"status": 0, "qty": 2, "expire_at": "+30min"}]
  },
  "fk_links": [{"orders.user_id": "users.id"}, {"orders.sku_id": "products.sku_id"}],
  "teardown": "delete_by_prefix"
}
```

**核心逻辑**：

1. **关联闭包**：从画像涉及的主表出发，沿外键双向扩展（上游必须存在、下游级联影响），直到闭包收敛。**外键关系优先取自 C3 的 DB 血缘（`FOREIGN_KEY_TO`），而非字段名启发式**；血缘缺失时才回退命名约定
2. **拓扑排序**：按外键依赖确定插入顺序；检测到循环依赖时断开最弱边（可空外键优先）并告警
3. **业务态构造**：从用例目标状态反推各表字段取值（如"测取消"→ orders.status=0 且未超时）
4. **读写表区分**：依据 C3 血缘，`WRITES_TABLE` 的表需**构造前置状态**（被测接口会改它），`READS_TABLE` 的表需**构造存在性**（被测接口会查它）——两者造数语义不同
5. **字段业务语义理解**：造数前必须先理解每个字段的**业务语义**（`status=0` 是"已取消"还是"待支付"），而非仅看类型。**语义分三层，来源与"可自动推导性"各不相同**，必须显式区分，否则会误以为"有了 DBML 就不用 A1 了"：

   | 语义层次 | 例子 | 来源 | 能否自动推导 |
   |---|---|---|---|
   | **① 结构语义**（是什么字段）| `amount`=金额、`status`=状态、`created_at`=时间 | 命名 + 类型 + semantic-field-types 12 类分类法 | ✅ 能（确定性 + LLM 辅助）|
   | **② 取值语义**（枚举每个值什么意思）| `status` 0/1/2 = 待支付/已支付/已取消 | DBML `enum`/`records`、DB `COMMENT ON`、代码常量折叠 | ⚠️ 部分能，缺失标 `inferred` |
   | **③ 业务语义**（在业务规则里的含义）| `status=0 且超时30min` = 可取消订单 | **仅 rules.json（A1 需求分析）+ A1.5 人工确认** | ❌ 不能从 DB/代码自动推导 |

   **关键红线**：① 结构语义靠分类法，② 取值语义靠 DBML/DB comment/常量折叠，但 **③ 业务语义的根来源是需求文档与业务知识，只存在于 rules.json，数据库和代码给不了**。DB 能告诉你 `status` 有 0/1/2 三个值，但给不了"status=0 且超时 30 分钟 ⇒ 可取消"这条规则——这正是 A1 需求分析存在的根本理由，**DBML/DB comment 只是取值语义的输入，不能替代 A1**。枚举取值从语义源取，不从 DB 现有数据猜
6. **表级数据模板**：唯一键随机化、枚举按语义源取值、decimal 精度、时间字段相对值（`+30min`）
7. **隔离与回收**：用例级前缀 `T{case_id}_`，执行后按主键回收；`keep-data` 调试模式保留

**关键设计决策**：

- 两条造数通道并存：**SQL 直插**（覆盖历史脏数据、边界状态）与**接口造数**（保证业务一致性）。默认 SQL 直插，涉及复杂业务约束的表切接口造数，策略按表配置
- 字段级约束 ≠ 业务约束（`qty ≤ 库存`）——业务约束从规则库推导，推不出的标记待人工补充，**不猜**
- **造数计划以 C3 血缘为事实源**：`fk_links` 由 `FOREIGN_KEY_TO` 直接生成，`tables_order` 由拓扑排序得出；血缘字段缺失时显式标 `inferred`/`unmapped`，不让造数器靠猜补外键

**异常与边界**：外键缺失（逻辑外键）时从设计文档/命名约定补推，标记 `inferred`；时间敏感数据统一用相对表达式，执行期求值；**C3 血缘标 `unmapped` 的表，造数计划须人工介入确认，不得自动直插**

**门禁**：造数执行成功率 ≥99%；外键闭包完整率 100%（对照人工分析）

**开源能力参照（复用而非重造）**：

> C5 的"理解业务语义 + 造数"两块，已有成熟开源工具各覆盖一部分。AstSight**不必从零实现通用造数**，但需看清"可复用"与"护城河"的边界：

| 环节 | 现成开源参照 | 与AstSight的关系 |
|---|---|---|
| 取值语义表达 | **DBML**（enum 枚举 + note 注释 + records 样例数据 + TableGroup 业务分组）| **是"表达语义的 DSL，不是推导语义的分析器"**——若被测项目提供 DBML，作为 C5 取值语义（②层）的最高优先级输入；未提供则回退 DB comment。它给不了③业务语义 |
| 字段语义分类字典 | **semantic-field-types**（12 大类语义分类法）| 作为 LLM 判定字段语义时的分类依据，替代凭空猜测 |
| 业务术语 → 字段映射 | **schemagate**（术语表 + MCP）| 对齐AstSight"术语表 + 规则库"长期记忆资产 |
| 外键闭包 + 拓扑排序造数 | **SeedKit** / **bloviate** | 通用造数机制（外键拓扑、环检测、种子可复现）可借鉴 |
| 逻辑外键补推 | **generate_synthetic_data**（`logical_fks`）| 与"物理外键/逻辑外键分离"同一红线，可借鉴其处理方式 |

**护城河（开源均未覆盖，须自研）**：上述工具只做"通用造数"——造出**合法、可复现**的数据，但**不携带业务意图**。它们造不出"`orders.status=0` 且 `created_at` 超 30 分钟且关联已实名用户"这种**针对特定测试场景、语义精确**的数据。AstSight的**业务态构造**（第 3 步：从用例目标状态反推字段取值）+ **变更驱动**（只造变更接口所需数据）正是别人没做的护城河，与通用造数器是"语义层"与"机制层"的分工。

### C4 用例设计

| 项  | 内容                                                            |
| -- | ------------------------------------------------------------- |
| 职责 | 基于画像与规则库生成分类业务用例集（数据形态，非代码）                                   |
| 输入 | api_profiles.json、rules.json、data_plan.json、changed_apis.json |
| 输出 | `testcases.json`                                              |

**用例类别与驱动源**：

| 类别   | 驱动源             | 断言设计                                  |
| ---- | --------------- | ------------------------------------- |
| 功能正向 | 画像出入参           | 状态码 + 响应字段存在性 + **DB 落库双向校验**         |
| 边界   | 三路约束最严值         | 边界点 ±1；含 DB 列宽边界（varchar(32) 的 32/33） |
| 负向   | 必填/枚举/类型约束      | 每必填字段 × 每非法形态，笛卡尔积经裁剪规则收敛             |
| 业务规则 | 规则库（仅 `active`，需求+设计双源） | 按**三件套**生成：正例 + 负例 + 边界（见 3.1.5）；断言须标注强度档 L1–L4，规则落在 L3/L4 时不得降级 |
| 变更回归 | changed_symbols | 打 `regression` 标签，形成本次变更必跑集           |

**用例间依赖**：

- 写操作产出的业务标识（produces）与下游入参（consumes）自动连线
- 依赖形式：`setup`（用例级前置造数）而非全局共享——避免状态污染（原型实测教训：多用例抢同一订单导致连环 409）

**关键设计决策**：

- 规则匹配采用打分制并设阈值，宁缺毋滥——误关联的规则会生成大量噪音用例（原型实测：打分制 + 字段校验后匹配准确率才达标）
- 每条用例携带 `source` 字段（规则编号/画像字段/变更符号），**全链路可追溯**；规则类用例另写 `RuleCoverage` 反向索引
- **`active` 规则的缺失是 C1 的输入缺口，不是 C4 的责任**——C4 不得用"多生成用例"掩盖规则缺失，缺就如实报缺
- 性能类规则（`type=performance`）自动带耗时断言，阈值取规则原文数值；原文无数值则记 `manual_required`

**门禁**：规则覆盖率 ≥80%（算法见 **3.1.5**，分母为 `active` 规则数、分子须含负例）；每用例断言非空率 100%；断言强度不应低于规则表达式所需档位（见 **3.1.6**）

### C6 用例编码

| 项  | 内容                                  |
| -- | ----------------------------------- |
| 职责 | 将用例集编译为可读、可改、可入库的 pytest 代码资产       |
| 输入 | testcases.json、data_plan.json       |
| 输出 | `tests/` 目录：conftest.py + 每接口一个测试文件 |

**生成物结构约定**：

- `conftest.py`：HTTP 客户端 fixture、造数器 fixture、DB 断言 fixture、用例级回收
- `test_<接口>.py`：类=接口，方法=用例；docstring 携带用例编号与规则溯源
- 依赖链**代码化**：上游响应值通过 fixture 上下文传递（可读优先），不做运行时字符串替换
- **人工保护段**：`MANUAL BEGIN/END` 标记内的内容在二次生成时保留
- 生成代码头部带生成时间、源契约版本、框架版本，便于审计

**关键设计决策**：

- **代码是资产不是黑盒**：生成后必须过人工 review 才能进用例库（幻觉在管道中放大，审核门不可省）
- 二次生成策略：契约未变的用例不重写；契约变化的用例生成 diff 报告，由人决定合并

**异常与边界**：LLM 参与的代码片段（复杂场景编排）必须经语法校验+导入校验双重自检，不通过则回退模板生成

**门禁**：生成代码可运行率 ≥95%（语法+导入+fixture 引用）；断言非空率 100%

### C7 执行验证与运行编排

> 运行层 = 数据冲突检测 → 并行调度 → 失败归因与重试 → 报告合并。目标是把"能跑"升级为"生产级稳定执行"：既不因数据竞争产生假失败，也不因偶发环境抖动污染门禁结论。

| 项  | 内容                                               |
| -- | ------------------------------------------------ |
| 职责 | 检测用例数据冲突 → 规划并行执行 → 执行 → 归因 → 有界重试 → 合并报告        |
| 输入 | testcases.json、data_plan.json、pytest 用例代码、运行环境配置 |
| 输出 | `report.json`（合并后的最终报告）+ 原始分片执行日志                |

#### C7.1 数据冲突检测

**目的**：并行前判断多个用例是否争用同一份数据，避免数据竞争导致的假失败。

**冲突判定维度**（数据维度，非资源维度）：

| 维度     | 判定                              | 冲突处理          |
| ------ | ------------------------------- | ------------- |
| 同一主键行  | 多用例操作同一 `(表, 主键值)`              | 冲突            |
| 同一唯一键值 | 共享种子数据中的同一唯一键（如固定 `sku_id`）     | 冲突            |
| 同一关联数据 | 多用例 share 同一上游 fixture（如共用同一订单） | 冲突            |
| 只读共享   | 多用例仅读同一数据、无写                    | **不冲突**，可安全并行 |

**冲突数据契约** `conflicts.json`：

```json
{
  "case_id": "TC-B-001",
  "resources": [
    {"table": "orders", "key": "order_no=ORD001", "mode": "write"},
    {"table": "products", "key": "sku_id=S001", "mode": "read"}
  ],
  "group": "share-orders-001",
  "parallel_group": "G1"
}
```

**核心逻辑**：

1. 从 DataPlan 与用例 setup 提取每个用例的**数据资源清单**（表 + 键 + 读写模式）
2. 两两比对：任一 `写` 资源交集 → 判冲突
3. 冲突用例聚合成**分组**（`group`），组内串行、组间并行；无冲突的用例进入默认并行池
4. 冲突分组的执行顺序按外键拓扑排序（保证造数前置）

**关键设计决策**：

- 冲突判定只看**数据维度**，不看接口维度——两个不同接口操作同一订单号同样是冲突
- 只读共享不冲突，这是并行度的关键来源：多数查询/列表用例可安全全并行
- 冲突检测是纯确定性逻辑（基于数据契约比对），不放 LLM

#### C7.2 并行调度

**调度模型**：

```
用例全集
   │ 冲突检测
   ▼
┌─────────────┬─────────────┬─────────────┐
│ 并行组 G1    │ 并行组 G2    │ 串行组 S1    │  ← 组间并行
│ (只读用例池) │ (独立写用例)  │ (冲突用例串行)│
└─────────────┴─────────────┴─────────────┘
```

**调度策略**：

- **组间并行、组内串行**：冲突用例在同一串行组内按序执行，组与组之间并行
- 并发度可配（`--workers N`，默认 = CPU 核数）；受外部资源限制时降级（数据库连接池上限、被测服务压力）
- 依赖链（produces→consumes）约束优先于并行度——有依赖的用例必须排在产出方之后

**关键设计决策**：

- 并行度不是越高越好：需按**被测服务的并发承受能力**设上限，避免把被测系统打挂后误判为失败（这本身就是一种需要归因的场景）
- 调度结果是**可重放的**（确定性分组），保证失败重跑时分组与顺序不变

#### C7.3 失败归因与自动重试

**归因分类**（区分"被测系统问题"与"测试侧问题"）：

| 归因类别            | 判定信号                     | 是否可重试       |
| --------------- | ------------------------ | ----------- |
| 被测系统缺陷（SUT bug） | 5xx、断言失败且响应符合契约、业务码非预期   | **否**（真实缺陷） |
| 测试侧数据问题         | 4xx 且源于造数缺失/脏数据          | 是（修复后重试）    |
| 测试侧用例问题         | 断言写错、参数构造错               | 是（修复后重试）    |
| 环境抖动            | 连接超时、DNS、网关 502、DB 锁等待超时 | 是（原样重试）     |
| 数据竞争残留          | 并发下偶发冲突、死锁回滚             | 是（降级串行重试）   |

**重试规则**：

1. 归因 → 仅"非被测系统问题"进入重试
2. 修复类（数据/用例）：应用修复动作后重试
3. 环境抖动类：原样重试，可加退避
4. **重试次数上限 3**（含首次执行共 4 次机会）；第 4 次仍失败 → 定为终态失败
5. 每次重试记录 `attempt`、`reason`、`action`，全程留痕

**重试数据契约**（报告内嵌）：

```json
{
  "case_id": "TC-B-003",
  "final_status": "pass",
  "attempts": [
    {"n": 1, "status": "fail", "reason": "env_flake", "action": "retry_as_is"},
    {"n": 2, "status": "pass"}
  ]
}
```

**关键设计决策**：

- **重试有界（≤3）且全程留痕**——重试是手段不是兜底，无限重试会把门禁结论拖成"永远在跑"
- 归因判定本身是确定性规则 + 阈值（如超时类错误码集合、DB 锁等待关键词），不放 LLM
- 归因不确定时**不重试**，标记 `unknown` 交人工——错误的重试会掩盖真实缺陷
- 数据竞争残留类重试**降级为串行**，验证是否并发导致的假失败

**归因双视角（重试视角 vs 根因归属视角）**：

本节的"归因分类"是从**重试视角**划分（决定"要不要重试、怎么重试"）。A5 诊断 Agent 另有一套**根因归属视角**的五类根因（决定"问题归谁、流向何处"）。两者不是一回事，是同一个失败的**两个正交切面**，映射如下：

| 重试视角分类（C7.3） | 根因归属视角（A5 五类根因） | action_target | 说明 |
|---|---|---|---|
| 被测系统缺陷（SUT bug） | `code_defect` | user | 真实缺陷，反馈用户修代码 |
| 测试侧数据问题 | `data_error` | framework | 造数能力缺口，回流框架升级 |
| 测试侧用例问题 | `case_error` | user | 用例/断言写错，反馈用户改用例 |
| 环境抖动 | （非根因，是重试理由） | — | 只决定"原样重试"，不参与归属 |
| 数据竞争残留 | （非根因，是重试理由） | — | 只决定"降级串行重试"，不参与归属 |
| —（C7.3 未单列） | `mock_error` | framework | Mock 语义模型覆盖不足，回流框架升级 |
| —（C7.3 未单列） | `change_induced` | user | 变更导致行为变化，反馈用户确认 |

> 关键：**重试视角的"环境抖动/竞争残留"不是根因，而是重试的触发信号**——它们不需要归属到 user/framework，重试通过即消除。真正的根因归属只看五类：`code_defect/case_error/data_error/mock_error/change_induced`，这五类才映射到 `action_target`（user/framework），进入 6.5 缺陷案例库的只有 `framework` 侧（`data_error`/`mock_error`）。详见 `agent-architecture.md` A5 章节与 `prompts/a5_result_diagnosis.md`。

#### C7.4 报告合并

**目的**：把多分片、多 attempt 的执行结果合并为一份终态报告。

**合并规则**：

1. 以 `case_id` 为聚合键，取最后一次 attempt 的终态
2. 统计口径分离：
   - **原始通过率**：首次执行通过数 / 总数
   - **最终通过率**：重试后通过数 / 总数（含重试恢复的用例）
   - **真实缺陷数**：归因为 SUT bug 的用例数（**门禁只认这一项**）
3. 报告输出维度：按用例类别、按接口、按归因类别三个切面汇总

**报告数据契约**：

```json
{
  "summary": {
    "total": 40,
    "final_pass": 38,
    "final_pass_rate": 0.95,
    "first_pass_rate": 0.88,
    "sut_defects": 2,
    "retried_recovered": 3,
    "unknown_attribution": 1
  },
  "by_category": {"functional": {"pass": 10, "fail": 0}, "...": {}},
  "by_endpoint": {"POST /api/orders": {"pass": 8, "fail": 1}},
  "by_reason": {"sut_bug": 2, "env_flake": 0, "data_issue": 0},
  "flaky_candidates": ["TC-B-003"],
  "token_usage": {
    "total_prompt": 182400,
    "total_completion": 96300,
    "total": 278700,
    "by_node": {
      "A1_requirement_analysis": 41500,
      "A4_case_design": 231200,
      "A5_result_diagnosis": 6000
    },
    "by_model": {"deepseek-v3": 278700},
    "estimated_cost": {"currency": "CNY", "amount": 0.84}
  },
  "gate": {"threshold": 85, "verdict": "pass"}
}
```

**关键设计决策**：

- **门禁只认"真实缺陷数"**，不认"最终通过率"——重试恢复的用例不计入通过率水分，SUT 缺陷不能被重试掩盖
- `flaky_candidates`（首次失败、重试通过且原因为环境抖动/竞争残留）单独列出，作为**被测系统稳定性信号**上报，而非简单归入通过
- **token 消耗统计**：按节点、按模型两个切面汇总，供成本治理与用量预警。统计范围仅覆盖三个含 LLM 的节点（A1 需求分析、A4 用例设计、A5 结果诊断），确定性能力服务（S2/S3）与工具零 token 不统计
- 报告保留原始分片日志，供归因复核

### C7.4.1 Token 消耗统计

> 目的：把"AI 测试全流程"的算力成本透明化，支撑成本治理、模型选型对比、用量预算预警。这是质量负责人视角的延伸——测试不仅要"测得对"，还要"测得起"。

**统计口径**：

| 维度 | 说明 |
|---|---|
| **按节点** | A1 需求分析 / A4 用例设计 / A5 结果诊断 三个 LLM 节点分别统计，定位"成本大头" |
| **按模型** | 不同 model 各自累加，支撑多模型成本对比与选型 |
| **按调用类型** | prompt（输入）/ completion（输出）分开，输出 token 通常是成本主因 |
| **按用例** | 可选细粒度：每条用例关联其生成/诊断消耗，定位"贵用例" |

**采集机制**：

1. **LLM 层统一埋点**：token 用量在 LLM 网关层采集（而非各 Agent 自行上报），保证口径一致、不遗漏。返回的 `usage.prompt_tokens / completion_tokens` 落一条 `TokenUsage` 记录
2. **节点归属标记**：每次调用带 `node` 标签（A1/A4/A5），由编排层在派发时注入
3. **重试计入**：A5 诊断的重试调用也计入（它们同样消耗 token），并在 `by_node` 中可区分"首次"与"重试"（可选）

**成本估算**：

- 维护一张**模型单价表**（`{model: {prompt_price, completion_price}}`，可配置），token × 单价 = 估算成本
- 单价表是**估算**，非精确计费——真实账单以云厂商为准，报告标注 `estimated_cost`
- 未配单价的模型 → 只统计 token，`estimated_cost` 置 null

**关键设计决策**：

- **采集放网关层，不放 Agent 内部**——Agent 只负责调用，token 计量是横切关注点，网关统一埋点才能保证"零遗漏、口径一致"
- **token 统计不进门禁**——它是观测指标，不是质量判定依据。成本超预算触发的是"预警"而非"阻断"（除非用户显式配置了成本上限门禁）
- **重试是成本放大器**：一次 A5 诊断失败重试 3 次，token 消耗 ×4。报告里应能看出"重试花了多少 token"，这本身就是"该不该优化归因准确率"的经济依据

**异常与边界**：某次调用未返回 usage（流式中断/上游异常）→ 该次 token 记为 0 并标记 `usage_missing`，不猜；成本单价未配置 → `estimated_cost=null`，仅输出 token 数

**门禁（可选）**：成本超预算预警阈值可配置，触发即告警但默认不阻断

**异常与边界**：重试次数耗尽仍失败 → 终态失败 + 完整 attempt 链；归因未知 → 不进重试、单独成列；调度阶段因外部资源不足无法并行 → 显式降级为串行并在报告标注

**门禁**：归因准确率 ≥85%（抽样人工复核）；假失败率（重试后证明非 SUT 问题）应持续低于阈值并作为回归监控项

## 五、横切设计

### 5.1 确定性边界（LLM 使用原则）

| 能力          | 是否用 LLM | 理由                          |
| ----------- | ------- | --------------------------- |
| C1 文档接入     | 部分      | 复杂语义段落理解是 LLM 主场；表格提取用确定性解析 |
| C2 变更感知     | 否       | git diff + 图谱追溯，纯确定性        |
| C3 接口画像     | 否       | 事实源，不容忍幻觉                   |
| C3.5 下游依赖控制 | 否       | 依赖识别与 Mock 编排，确定性           |
| C5 数据准备     | 否       | 约束推断/拓扑排序，确定性               |
| C4 用例设计     | 部分      | 业务场景联想用 LLM；约束类用例用模板        |
| C6 用例编码     | 部分      | 标准用例模板生成；复杂编排可用 LLM 但双重自检   |
| C7 执行验证     | 否       | 执行与归因，确定性                   |

### 5.2 异常处理总原则

1. **事实源环节（C2/C3/C5）失败即中止**——上游错了下游全是垃圾
2. **生成环节（C4/C6）失败可降级**——LLM 失败回退模板，模板失败跳过该接口并记录
3. **所有降级必须显式标记**在报告中，不允许静默

### 5.3 可追溯性

每个最终产物都能反向溯源：报告中的失败 → 用例 → 规则编号/变更符号 → 文档章节/git 提交。溯源链断任何一环都视为设计缺陷。

**证据等级（evidence）贯穿全程**：每条画像/血缘/造数字段必须带 `verified/inferred/unmapped` 三级证据标记，报告与门禁可据此区分"已验证事实"与"推断值"，保证"事实源零 LLM、不臆造"可被机器审计（对齐 CodeGraph 的 `FACT/POSSIBLE/UNKNOWN` 诚实标记）。

### 5.4 扩展点

| 扩展点             | 机制                                  |
| --------------- | ----------------------------------- |
| 新 Web 框架路由识别    | C2 路由插件接口                           |
| 新文档格式           | C1 解析器插件                            |
| 新数据库方言          | C5 DDL 解析方言包                        |
| 对接测试平台          | C7 报告适配器（TestHub REST 推送）           |
| 断言库扩展           | C4/C6 断言类型注册表                       |
| 下游依赖注入点         | C3.5 注入点插件（HTTP 代理/SDK 注入/MQ topic） |
| Mock/Sandbox 后端 | C3.5 替身服务接入适配器                      |
| LLM 模型接入        | LLM 网关适配器（不同 provider 的 usage 字段差异归一）   |
| 模型单价表           | C7.4.1 成本估算配置（prompt/completion 单价，可热更） |

## 七、风险与对策

| 风险                     | 等级 | 对策                                             |
| ---------------------- | -- | ---------------------------------------------- |
| Java/Spring 路由识别精度不足   | 高  | 先用 5 个真实项目实测；不达标则 Java 栈仅启用"路径启发式+人工确认"模式      |
| 设计文档格式千差万别             | 高  | 先限定 Markdown 表格型字段定义；其他格式走 LLM 精读+人工复核         |
| 逻辑外键（无 DDL 约束）导致闭包不完整  | 中  | 命名约定补推 + 设计文档表关系章节 + inferred 标记人工确认           |
| 生成用例通过率虚高（断言过宽）        | 中  | 门禁看断言强度指标（字段级断言占比），不只看通过率                      |
| 业务约束推不出（qty≤库存类）       | 中  | 规则库显式表达；推不出标记待人工，不猜                            |
| 数据库直连权限与安全             | 中  | 默认只读结构（information_schema）；造数仅在独立测试库，连接串按环境隔离  |
| 下游依赖无法识别（动态调用/配置化 URL） | 中  | 标记 unidentified 人工补画像；报告显式告警，不静默透传             |
| Mock 注入失效导致真实透传（资损风险） | 高  | 透传熔断护栏：执行层监控所有出站请求，任何真实透传立即阻断；side_effect.has=true 的下游熔断优先级最高 |
| Mock 响应与 DB 造数变量域不一致   | 中  | Mock 与 DB 造数共享同一变量域（T{case_id}_ 前缀），门禁校验两者对齐   |
| Mock 语义失真导致假绿          | 高  | C3.5.1 语义模型：契约+业务知识+用例意图三层定语义，分支覆盖率门禁 100%     |
| 下游语义信息缺失（无文档无源码）       | 中  | C3.5.2 三档渐进：档1文档先行跑通，档2补源码跑准；缺口显式标记不假装完整       |
| token 成本失控（全流程 AI 测试烧钱）   | 中  | C7.4.1 统一计量 + 按节点/模型定位成本大头；重试归因优化是降本主抓手；超预算预警 |

## 八、实施顺序（设计确认后的工程排期参考）

| 迭代   | 范围                        | 出口标准           |
| ---- | ------------------------- | -------------- |
| 迭代 0 | **3.1 规则库**：C1 抽取 → `RuleSet` → `RuleBinding`/`RuleCoverage` → C7 判定接线 | 单域 ≥20 条 `active` 规则，其中 ≥70% 有 `expression`；规则覆盖率可算出；对一个变异体给出存活/杀死的确定结论 |
| 迭代 1 | C2 变更感知（Python 栈路由插件）     | 召回率/误报率达标；路由审计报告 `matched` 占比达标（双源交叉命中） |
| 迭代 2 | C5 数据准备（外键闭包+SQL 造数）      | 订单场景 3 表闭包造数成功 |
| 迭代 3 | C6 用例编码（模板引擎+conftest 约定） | 可运行率 ≥95%      |
| 迭代 4 | C1 设计文档解析 + C3 三路校验 + 端到端 | 真实项目单分支全流程跑通   |

> 本说明书为设计基线 v2.16。后续实现阶段任何对本契约的偏离，需回写本文档并升版本号。

> **排期说明**：`full` 模式是入场路径，不是可选项——迭代 1 的出口标准应补一条「`full` 在单仓跑通并产出契约基线」，否则 `delta` 没有基线可维护，迭代 2 之后全部悬空。

> **排期说明（v2.15）**：迭代 0 之所以排在 C2 之前，因为 C4 与 C7 都以规则库为输入——不做规则库，C4 只能退化成"按画像字段拼用例"，C7 只能判状态码和字段存在性，整条链路回到 2.0。若坚持先做变更感知，则迭代 4 端到端跑通前必须先补回迭代 0，否则端到端只能验证"跑得通"，验证不了"判得对"。
