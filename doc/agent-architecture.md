# AstSight Agent 架构设计（DeepAgents × CodeGraph × LangGraph）

> 项目名：**AstSight**（AST + Sight）｜ CLI：`astsight` ｜ Maven：`io.astsight:astsight-core`
> 本文回答两个问题：**框架需要几个 Agent**、**每个 Agent 的内部架构是什么**。
> 技术栈：DeepAgents（多智能体编排框架）+ CodeGraph（代码图谱基础设施）+ LangGraph（图式状态机编排）。
> 前置文档：`framework-capability-design.md`（能力设计 v2.15）。本文是能力设计在技术实现层的落点，非替代。

> **⚠️ 已取代（2026-10-26）**：本文中的 **A1 规则抽取 / A1.5 规则人工确认 / C1 规则库**
> 链路已被实现层取代。当前编排为 **A1 需求上下文 → A4 用例导入 → A4.5 审核结果检查 → C6**：
>
> - 需求文档 + OpenAPI 先产出 `context.json` / `prompt.md` / `cases.schema.json`；
> - Skill 或人工写出用例草案，`cases import` 只生成待审 proposal；
> - 人工审核后 `cases approve` 才写入版本化 `caseset.json`；
> - 未审核/审核未通过时在 A4.5 阻断，不进入 C6。
>
> A4.5 不再检查“高风险规则是否确认”，而是检查“待审用例是否全部决定且至少有一条可执行用例”。
> 相关章节保留为历史设计推演，与实现冲突时以 `engine/orchestration/` 与
> `engine/astsight/cases/` 为准。

## 一、Agent 切分原则（为什么是这几个，不是按能力 1:1）

**核心原则：Agent 的边界按"是否需要 LLM 自主决策"切分，不按能力清单机械映射。**

| 判据 | 结论 |
|---|---|
| 需要 LLM 自主决策（理解/推理/生成） | → 做成 **Agent**（智能体） |
| 纯确定性逻辑（解析/计算/追溯/执行） | → 做成 **能力服务（Capability Service）**，即多个工具的编排封装 |

> **能力服务 ≠ Agent**。能力服务是"纯确定性工具的流水线封装"，有固定的输入输出契约、无 LLM、无自主决策、无 prompt；Agent 是"带 prompt、会思考、能自主决策"的智能体。二者在编排图上都是节点，但性质完全不同——**不能因为"它在编排图上是节点"就把它叫 Agent**。

**反面教训（TestGen AI）**：把 9 个纯模板活也做成 Agent，结果全是空壳 prompt、九选一单选路由，不是真正的多智能体协作。本设计避免重蹈：确定性能力全部下沉为**能力服务**，Agent 只保留"需要思考"的部分。

---

## 二、总体：3 个 Agent + 2 个能力服务 + 1 个编排层 + 1 套共享工具

```
                     ┌─────────────────────────────────────────┐
                     │        Orchestrator（编排器）             │
                     │   LangGraph StateGraph 根节点             │
                     │   入口分流：需求变更? / 代码变更?           │
                     └───────────────┬─────────────┬───────────┘
                                     │             │
             ┌───────────────────────┘             └───────────────────────┐
             ▼（文档变更）                                                      ▼（代码变更）
   ┌───────────────┐                                            ┌───────────────────┐
   │ A1 需求分析    │                                            │ S2 变更感知 (服务) │
   │ 文档→规则 (Agent)│                                            │ 分支差异→变更接口   │
   └───────┬───────┘                                            └─────────┬─────────┘
           ▼                                                                │
   ┌───────────────┐                                                        │
   │ A1.5 人工确认  │ ◄── 人工断点：高风险未确认则阻断                        │
   │ 高风险必确认    │                                                        │
   │ 低风险 auto 放行│                                                        ▼
   └───────┬───────┘                                            ┌───────────────────┐
           │（确认通过的 rules）                                  │ S3 画像构建 (服务) │
           └───────────────────────────────┬────────────────────│ 接口→档案+下游依赖 │
                                            ▼                    └───────────────────┘
                              ┌───────────────────────┐
                              │  共享工具层（Tools）     │
                              │  CodeGraph 客户端       │
                              │  接口解析器 / DB 分析器  │
                              │  造数器 / Mock 编排器   │
                              │  执行器 / 报告器        │
                              └───────────┬───────────┘
                                          ▼
                              ┌───────────────────────┐
                              │ A4 用例设计 (Agent)    │
                              │ 画像+规则 → 用例 → 代码 │
                              └───────────┬───────────┘
                                          ▼
                              ┌───────────────────────┐
                              │ A5 结果诊断 (Agent)    │
                              │ 失败 → 归因 → 重试决策 │
                              └───────────────────────┘
```

**节点职责速览**：

| 节点 | 对应能力 | 形态 | 需要 LLM 吗 | 职责一句话 | 触发条件 |
|---|---|---|---|---|---|
| A1 需求分析 | C1 | **Agent** | 是（重） | 文档 → 结构化业务规则 | 需求/设计文档有变更 |
| A1.5 规则确认 | C1 | **人工断点** | 否 | 高风险必确认、低风险 auto 放行 | 跟随 A1，未确认高风险则阻断 |
| S2 变更感知 | C2 | **能力服务** | 否 | 分支差异 → 变更接口列表 | 代码分支有变更 |
| S3 画像构建 | C3 / C3.5 | **能力服务** | 否 | 接口 → 完整档案+下游依赖 | 跟随 S2 |
| A4 用例设计 | C4 / C6 | **Agent** | 是（重） | 画像+规则 → 用例 → pytest 代码 | 事实源就绪后 |
| A5 结果诊断 | C7.3 | **Agent** | 是（弱） | 失败 → 归因 → 重试决策 | 执行失败时 |
| — Orchestrator | 全流程 | 编排器 | 是（调度） | 串起全链路，管理状态 | — |

> 注：C5 数据准备、C6 的模板编码、C7.1/C7.2/C7.4 均为**确定性工具**（图中归入共享工具层）。S2、S3 是两个**能力服务**（多工具流水线封装），不是 Agent。A1 与 S2 是**两个独立入口**，分别对应"需求变更"与"代码变更"，可独立触发也可同时触发。

## 三、每个节点的架构

> 统一用"输入 → 内部节点（LangGraph 子图）→ 输出 → 关键决策"描述。Agent 和能力服务自身都是一个 LangGraph 子图（subgraph），可独立运行、可被编排器调度。区别仅在：Agent 内部有 LLM 节点 + prompt，能力服务内部全为确定性节点。

### A1 需求分析 Agent（文档 → 业务规则）

**职责**：把非结构化文档变成结构化字段级业务规则（`rules.json`）。

```
输入：需求文档 + 设计文档
      │
      ▼
┌─────────────────────────────────┐
│ 1. 文档切块节点（确定性）          │  按标题层级切块，识别章节类型
│ 2. 表格提取节点（确定性）          │  设计文档字段定义表 → 结构化
│ 3. 规则提取节点（LLM）            │  文本语义 → 规则条目（字段约束/流程/性能/权限）
│ 4. 冲突裁决节点（确定性）          │  设计文档 > 需求文档；冲突记 conflict
│ 5. 规则校验节点（确定性）          │  编号、字段名、来源完整性校验
└─────────────────────────────────┘
      │
      ▼
输出：rules.json（规则集合，含来源溯源）
```

**关键决策**：
- **LLM 只用在第 3 步**（语义理解），切块/表格/校验/裁决全是确定性——这是"LLM 只干它擅长的"的落地
- 规则产出必须带 `source`（文档+章节+版本），支撑全链路溯源
- 规则产出后进入 **A1.5 规则人工确认**（见下节）：高风险（P0/高风险 P1）必确认、不确认即阻断；低风险 auto 放行。LLM 输出经 schema 校验，未过校验回退人工
- **主提示词**（历史）：`prompts/a1_requirement_analysis.md`——定义角色、规则提取方法论、输出契约（对齐 rules.json 字段，含 P0/高风险 `reasoning` 留痕）、需求缺口红线（标注待确认、不臆造假设）。该提示词已随规则层删除；当前生成契约见 `prompts/requirements_to_cases.md`

### A1.5 规则人工确认环节（A1 产出 → 确认入库）

**定位**：A1 是"发散"，会挖出大量规则（含缺口、冲突、高风险推断）。规则库是下游 S3/C4/C5 的**事实源**，一条错误规则会污染到用例、造数、Mock 全链路（假绿）。因此规则入库前必须过**人工确认**——这是框架「A1 发散 → 人工确认 → A4 收敛」三段式里承上启下的闸门。

#### 核心闸门规则：高风险必确认、不确认即阻断；低风险免确认直接放行

人工确认的输入是 A1 的 `rules.json` 初稿。规则按风险**二分类**，没有中间地带：

| 分类 | 规则范围 | 是否需确认 | 放行条件 |
|---|---|---|---|
| **高风险** | 所有 `P0` + 高风险 `P1`（资金/权限/数据一致性/核心状态流转）| **必须确认** | `confirm.status=confirmed` 才放行；**未确认即阻断** |
| **低风险** | 普通 `P1`（非高风险主题）+ `P2` + `P3` | **免确认** | 自动放行，直接标记 `auto` |

> **高风险规则：不确认就阻断。** 只要存在一条未确认的高风险规则，Orchestrator 就不得进入 A4 用例设计——宁缺毋滥，防止未确认的高风险规则直接生成用例 → 假绿。
>
> **低风险规则：免确认直接放行。** 人工注意力是稀缺资源，不值得花在普通 P1/P2/P3 上。低风险规则不需要人逐条过，由系统自动标记放行，仅保留事后抽查通道。
>
> `reasoning` 留痕只为**高风险**这一层服务——确认人靠它反查"模型为什么这么判"，而不是从零重读文档。这正是方案 B 留痕（只 P0/高风险留痕）的价值：**把有限的人工注意力 100% 压在高风险规则上，低风险不消耗人工。**

#### 确认人只做四件事（全部针对高风险规则）

确认人**只处理高风险规则**，低风险规则无需介入：

1. **判定**：对每条高风险规则给出 `confirmed`（确认）或 `rejected`（驳回）。
2. **修正**：规则方向对但表述/字段/定级有误时，直接改（如修正 `fields`、`priority`、`source`）。
3. **裁决冲突**：A1 标注 `【冲突】` 的规则，确认人必须**二选一或合并**，不得让冲突进入下游。
4. **补缺口**：A1 标 `【待确认】` 的规则，确认人要么补上真实约束，要么明确"该约束本期不做"（标记 `deferred`）。

#### 确认结果如何回写

在 `rules.json` 每条规则上追加**确认状态字段**（与 A1 产出字段并存，A1 本身不写这些）：

```json
{
  "id": "BR-01",
  "text": "创建订单时若商品库存不足，应返回 40001",
  "priority": "P0",
  "reasoning": "依据 requirement.md 第 3.2 节「库存校验」的「库存不足返回 40001」推断",
  "confirm": {
    "status": "confirmed | rejected | deferred | auto",
    "by": "人工确认人标识（auto 时为空）",
    "at": "2026-10-20T16:00:00+08:00",
    "note": "可选：修改说明 / 驳回原因"
  }
}
```

> `status=auto` 是低风险规则**免确认自动放行**的状态，由 Orchestrator 在 A1 产出后自动写入，`by` 为空，不需要人工介入。

#### 入库与流转规则

- **放行两类**：① 高风险 `confirmed`；② 低风险 `auto`。两者剥离 `reasoning`（留痕不进下游）后写入正式 `rules.json`，供 S3/C4/C5 消费。
- **`rejected`**：不入库，但保留在确认报告里（A1 下次可据驳回原因收敛提取策略）。
- **`deferred`**：本期不测，标记但**不删除**，保留在规则库的 deferred 区，供下一轮变更时重新评估。
- **阻断条件（唯一）**：存在**未确认的高风险规则**（即 P0/高风险 P1 尚未被人工标为 `confirmed`/`rejected`/`deferred`）时，**Orchestrator 必须阻断**，不得进入 A4。低风险规则的 `auto` 不参与阻断判断。

#### 与 6.5 历史缺陷案例库入库的区别

| 维度 | A1.5 规则确认 | 6.5 缺陷案例入库 |
|---|---|---|
| 确认对象 | A1 产出的业务规则 | A5 归因出的框架缺陷 |
| 时机 | 用例生成前（C4 之前）| 报告合并后（框架迭代用）|
| 目的 | 防止错误规则污染下游 | 防止错误案例污染框架改进依据 |
| 状态字段 | `confirm.status`（confirmed/rejected/deferred/auto）| `review.status` |

> 两者共同原则：**LLM 只做初判，人工做终审；AI 判断永远明示为 AI 判断，人工结论单独记录，不混在一起。**

### S2 变更感知能力服务（分支差异 → 变更接口）

**职责**：从 git 分支差异精确推导受影响接口（`changed_apis.json`）。

```
输入：仓库 + base/target 分支
      │
      ▼
┌─────────────────────────────────┐
│ 1. git diff 节点（确定性）         │  变更文件 + 函数级 AST diff
│ 2. 图谱追溯节点（确定性，CodeGraph）│  反向追溯至路由层（深度可配）
│ 3. 路由匹配节点（确定性，插件）     │  FastAPI/Flask/Django/Spring
│ 4. 置信度判定节点（确定性）         │  high/medium/low
│ 5. 低置信度分流节点（确定性）       │  仅列报告供人工勾选，不进下游
└─────────────────────────────────┘
      │
      ▼
输出：changed_apis.json（含 confidence + trace 链）
```

**关键决策**：
- **纯确定性，零 LLM**——变更感知要的是精确，不是创造力。原"弱 LLM 复核"改为人工复核（编排层的人工断点），避免为一句可读性描述引入不确定性
- 低置信度**不进入下游**，只在报告列出供人工勾选
- 语言不支持 → 该文件/符号跳过，不做降级兜底（见下）

**CodeGraph 接入方式（代码嵌入）**：

> 第 2 步「图谱追溯」依赖 CodeGraph（`colbymchenry/codegraph`）。本节点通过**代码嵌入**接入：常驻 Node worker 进程内直接 `import` 其库 API，经 stdio JSON 调用；**不走 MCP**（MCP 返回面向模型阅读，非结构化事实源），CLI 仅用于诊断。**不自研 AST 图谱**，但**自研路由插件**——理由见下。

- **接入方式**：S2 调 `getImpactRadius` / `getCallers` / `getCallees` 做反向追溯；AstSight 只做"编排 + 证据等级判定 + 分流"
- **符号级 → 接口级的换算必须显式做**：`impact` 给的是符号闭包，C2 要的是接口清单。客户端内部与路由表求交后返回 `affected_routes`，**不允许**把符号名列表当接口清单上报
- **深度用尽即降级**：`depth_used >= depth` 时标 `truncated`，证据等级不得升为 `verified`（闭包可能没走完）
- **语言不支持 → 直接跳过**：该变更符号标记 `unsupported` 并从变更集剔除，报告显式列出"因语言不支持未追溯的符号"——**宁可漏，不可错**
- **证据等级自行判定**：实测 CodeGraph 不输出 `FACT/POSSIBLE/UNKNOWN` 字段，`evidence` 由 AstSight 按「双源独立一致 → `verified`；单源 → `inferred`；冲突 → `unmapped`」判定

### S3 画像构建能力服务（接口 → 完整档案 + 下游依赖）

**职责**：为变更接口建立唯一事实源（`api_profiles.json`）。

```
输入：ChangedAPI[] + OpenAPI + DDL + rules + 术语表
      │
      ▼
┌─────────────────────────────────┐
│ 1. 契约提取节点（确定性）          │  OpenAPI 提取；缺失则标记 contract_incomplete
│ 2. DB 映射节点（确定性）          │  字段↔表列映射，命名归一
│ 3. 三路约束校验节点（确定性）      │  OpenAPI/DB/规则 取最严，记冲突
│ 4. 下游识别节点（确定性，CodeGraph）│ 正向追溯出站调用（HTTP/MQ/Redis/...）
│ 5. 语义附着节点（确定性）          │  术语表 + 规则命中 + DB comment
└─────────────────────────────────┘
      │
      ▼
输出：api_profiles.json（含 downstream_deps + side_effect 护栏标记）
```

**关键决策**：
- **纯确定性，不放 LLM**——画像是下游一切的事实源，错一处全盘错。这也是它必须做成能力服务（而非 Agent）的根本原因：Agent 的自主性在事实源环节是风险而非收益
- 下游识别的副作用字段已降级为"安全护栏标记"（见 v2.9），只需标出资损类写操作
- 画像构建常与 S2 串行：S2 输出 changed_apis → S3 只画像变更接口（避免全量画像浪费）

**CodeGraph 接入方式（与 S2 同源，代码嵌入）**：

> S3 的第 4 步「下游识别」，与 S2 共用**同一个 worker 进程与同一份图谱索引**（一仓一实例），只是遍历方向相反：S2 反向（变更→路由），S3 正向（路由→下游）。

| 节点 | CodeGraph 可提供 | 映射的AstSight字段 |
|---|---|---|
| 路由清单（第 1 步） | `getRoutingManifest` + `getNodesByKind("route")`，**仅供交叉校验** | `apis[]` 的 handler 绑定 |
| 下游识别（第 4 步） | `getCallees` 递归 + ORM/HTTP client/MQ SDK 调用点 | `downstream_deps[]`（下游调用链） |
| DB 映射（第 2 步） | **仅到 ORM/mapper 调用点**，无表列级血缘 | `db_mapping` 的**候选**，须 DDL 侧确认 |

- **路由必须先过插件**：实测 `getRoutingManifest` 对 Flask `url_prefix` 与 Django `include()` 的前缀不拼接、对 `@app.get/@app.post` 完全不识别、对 Django 不产出 HTTP method。直接采信会生成缺前缀的 URL，请求 404 且**失败归因到无关模块**。因此路由以框架插件为主、图谱为辅，交叉校验后才定等级
- **一源两用**：避免重复建图；但注意一仓一写者——S2/S3 并发时索引写入需串行化
- **语言不支持 → 直接跳过**：下游识别直接跳过并标 `unsupported`，报告显式列出"未识别下游的接口"——宁可漏，不可错
- **DB 血缘的边界（更正）**：CodeGraph **不提供** `READS_TABLE`/`WRITES_TABLE`/`MAPS_TO_TABLE` 这类表列级血缘（那是独立项目 `raghurammrsd/CODE_GRAPH_MCP` 的能力，不可混用）。图谱最多追到 ORM / mapper 调用点；列级 `DBLineage` 仍靠 DDL + SQL 解析 + 设计文档，原生 SQL 字符串尤其超出图谱能力。画像须显式区分"ORM 可证血缘"与"原生 SQL 待补"

### A4 用例设计 Agent（画像+规则 → 用例 → pytest 代码）

**职责**：生成分类用例并编码为 pytest 资产（`testcases.json` → `tests/`）。这是唯一"重 LLM"的 Agent。

```
输入：api_profiles + rules + data_plan + changed_apis
      │
      ▼
┌─────────────────────────────────┐
│ 1. 模板用例生成节点（确定性）      │  正向/边界/负向/安全 四类模板用例
│ 2. 业务场景生成节点（LLM）        │  规则+画像 → 业务用例（场景联想）
│ 3. 规则匹配打分节点（确定性）      │  打分≥阈值才关联，宁缺毋滥
│ 4. 依赖连线节点（确定性）         │  produces/consumes → setup/变量传递
│ 5. 语义绑定节点（确定性）         │  用例 → Mock 语义分支（C3.5.1）
│ 6. 代码生成节点（LLM+模板混合）   │  模板为主，复杂编排用 LLM
│ 7. 代码校验节点（确定性）         │  语法+导入+fixture 引用双重自检
└─────────────────────────────────┘
      │
      ▼
输出：testcases.json + tests/*.py（含人工保护段）
```

**关键决策**：
- **LLM 只用于第 2、6 步**（业务场景联想、复杂代码编排），其余全确定性模板——这是"LLM 用在刀刃上"的落地
- 第 7 步校验不通过 → 回退模板生成，不赌 LLM
- 生成代码过人工 review 才入库（审核门，幻觉在管道放大）
- **主提示词**（历史）：`prompts/a4_case_design.md`——收敛版，LLM 只做"业务场景联想"（给定定型规则，联想触发场景），**禁止发散新规则、编造字段/断言值**；边界值/依赖连线/Mock 绑定由确定性节点做。该提示词已删除；当前生成契约见 `prompts/requirements_to_cases.md`

### A5 结果诊断 Agent（失败 → 归因 → 重试决策）

**职责**：对失败用例自动归因，决定是否重试（`report.json` 的归因部分）。

```
输入：失败用例 + 执行上下文（响应/日志/环境）
      │
      ▼
┌─────────────────────────────────┐
│ 1. 信号提取节点（确定性）          │  状态码/异常类型/断言详情/耗时
│ 2. 归因分类节点（确定性规则为主）  │  五类根因：code_defect/case_error/data_error/mock_error/change_induced
│ 3. 疑难归因节点（LLM，可选）      │  规则判不了的复杂失败 → LLM 辅助（兜底）
│ 4. 动作归属节点（确定性）         │  user（反馈用户）vs framework（回流框架升级）
│ 5. 重试决策节点（确定性）         │  仅非 SUT 问题重试，≤3 次，留痕
└─────────────────────────────────┘
      │
      ▼
输出：归因结果（root_cause + action_target + confidence）+ 重试计划（喂给执行器）
```

**关键决策**：
- **归因主体是确定性规则**（错误码集合、超时关键词、DB 锁等待特征），LLM 只兜底疑难项
- **五类根因 + 动作归属路由**：`code_defect`/`case_error`/`change_induced` → `user`（反馈用户改进）；`data_error`/`mock_error` → `framework`（回流框架升级）。判定要点：用户资产写错→user，框架能力不足→framework
- **归因不确定 → 不重试**，标 `unknown` 交人工——错误重试会掩盖真实缺陷
- SUT bug **永不重试**，这是铁律
- **主提示词**：`prompts/a5_result_diagnosis.md`——只驱动第 3 步疑难归因节点，输出契约含 `root_cause`（五类）/`action_target`（user|framework）/`confidence`（诚实原则：证据不足必 low）/`evidence`（可溯源）/`verify_action`

## 四、Orchestrator（编排器）架构

**职责**：用 LangGraph StateGraph 串起 3 个 Agent（A1/A4/A5）+ 2 个能力服务（S2/S3）+ 确定性工具，管理全局状态与流转。

```
State（全局共享状态）：
  changed_apis / profiles / rules / data_plan / cases / report / 门禁结论

流转图（主流程，含入口分流 + 人工断点 + 执行子图）：
  START

                                        [工具] C5 数据准备
                                               ▼
                                        A4 用例设计
                                               ▼

                                               ▼
                          [工具] C7.2 并行调度
                                               ▼
                          ╔═══════════════════════════════╗
                          ║  [执行编排子图 C7]（详见 5.1）   ║
                          ║  ┌─────────────────────────┐  ║
                          ║  │ 执行（单用例执行器 × N）  │◄─┐║
                          ║  │ 六阶段：造数→Mock→请求    │  │║
                          ║  │  →断言→熔断→数据清理      │  │║
                          ║  └───────────┬─────────────┘  │║
                          ║              ▼                │║
                          ║        ┌─────┴──────┐          │║
                          ║        │ 有失败？     │          │║
                          ║        └─────┬──────┘          │║
                          ║      ┌───────┴────────┐        │║
                          ║      ▼                ▼        │║
                          ║  A5 结果诊断      全部通过       │║
                          ║  （Agent,兜底）      │          │║

                          ║    └────┼────────────┘          │║
                          ║         ▼                       │║
                          ║  （回环只回"执行"节点）           │║
                          ║     └──────────────────────────┘║
                          ╚═══════════════════┬═════════════╝
                                               ▼
                          [工具] C7.4 报告合并 → 门禁判定 → END
```

**关键设计**：
- **入口分流**：框架有两个变更源——**需求/设计文档变更**（触发 A1）和**代码分支变更**（触发 S2）。二者可独立发生，也可同时发生。A1 只跑"本次需求文档有更新"时才需要；纯代码变更（如改了个 bug）不触发 A1，直接走 S2 这条线。
- **A1.5 人工断点**：A1 产出 `rules.json` 后，Orchestrator 检查**是否存在未确认的高风险规则**（P0/高风险 P1 未标 `confirmed/rejected/deferred`）。存在则**阻断**，等待人工确认；低风险规则自动标 `auto` 放行，不阻断。确认通过后 rules 汇入 State，供下游 S3/C4/C5 消费。
- **执行子图（C7）**：冲突检测 + 并行调度 + 执行 + 归因 + 重试，整体封装为一个 LangGraph 子图（详见 5.1），主流程只看到"执行子图"这一层。子图内部有自己的状态机（scheduled→executing→diagnosing→retrying→reporting），重试回环**只回子图内的"执行"节点**，不冒出到主流程。
- **条件分支**：执行子图内 A5 诊断出"可重试" → 回环到子图内执行节点；诊断出"终态" → 子图返回主流程，进入报告
- **失败即中止**：事实源环节（S2/S3/C5）失败 → 直接终止，不回退硬跑
- **其余人工断点**：审核门（A4 产出代码后）、低置信度确认（S2）作为**人工交互节点**插入图，需人工放行才继续

**DeepAgents 的角色**：
- DeepAgents 提供 Agent 的**声明式定义**（prompt + 工具绑定 + 子 agent 描述），以及**人机协作审核门**（Agent Inbox 模式）
- LangGraph 提供**确定性编排骨架**（状态图、条件分支、回环）
- 两者分工：**DeepAgents 管 Agent 本体，LangGraph 管 Agent 之间的流转**——各用所长，而非二选一

## 五、共享工具层（Tools，非 Agent）

| 工具 | 对应能力 | 是否 LLM | 说明 |
|---|---|---|---|
| CodeGraph 客户端 | 基础设施 | 否 | 反向/正向追溯、变更 diff |
| 接口解析器 | C3 | 否 | OpenAPI/YAML/$ref |
| DB 分析器 | C5 | 否 | DDL 解析、外键闭包 |

---

### 5.1 执行编排（C7）展开

> 定位：`framework-capability-design.md` 的 C7 章节讲的是**能力设计**（做什么——冲突检测/并行调度/归因重试/报告合并）。本节讲的是**编排细节**（怎么串——执行周期状态机、单用例执行器机制、Mock 编排与熔断护栏的运行时时序）。两者是"能力"与"编排"的分层，不重复。

执行编排由三块组成，构成一个完整闭环：

1. **执行周期状态机**——管"整个执行周期怎么流转"（调度→执行→归因→回环→报告）
2. **单用例执行器机制**——管"一个用例怎么真正跑起来"（造数→Mock→HTTP→断言→熔断监控→数据清理）
3. **Mock 编排与熔断护栏**——管"跑的时候下游怎么拦截、透传怎么熔断"

#### 5.1.1 执行周期状态机（LangGraph 子图）

执行器整体是一个 LangGraph 子图，内部状态机如下：

```
                    ┌─────────────────────────────┐
                    │  [工具] C7.1 冲突检测          │
                    │  输入：cases + data_plan      │
                    │  输出：conflicts.json(分组)    │
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │  [工具] C7.2 并行调度          │
                    │  输入：conflicts 分组          │
                    │  输出：执行计划(组间并行/组内串行)│
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
                    │  [工具] 执行（单用例执行器 × N） │ ◄─┐
                    │  每个用例走 5.1.2 的执行器机制   │   │
                    └──────────────┬──────────────┘   │
                                   ▼                   │
                          ┌────────┴────────┐          │
                          │  有失败？         │          │
                          └────────┬────────┘          │
                     ┌─────────────┴─────────────┐     │
                     │ 是                        │ 否  │
                     ▼                          ▼     │
              ┌──────────────┐           ┌────────────┐│
              │ A5 结果诊断    │           │ [工具] C7.4 ││
              │ (Agent, 兜底) │           │ 报告合并     ││
              └──────┬───────┘           └─────┬──────┘│
                     │                          ▼      │
              ┌──────┴───────┐              ┌─────────┐ │
              │ 归因=可重试？  │              │ 门禁判定  │ │
              └──────┬───────┘              └────┬────┘ │
            ┌────────┴───────┐                   ▼     │
            │ 是(≤3次)        │ 否              END     │
            ▼                ▼                          │
      ┌────────────┐  ┌──────────────┐                 │
      │ 回环到执行   │  │ 终态 → C7.4   │                 │
      └─────┬──────┘  └──────────────┘                 │
            └──────────────────────────────────────────┘
```

**状态机关键点**：

| 要素 | 设计 |
|---|---|
| 状态 | `scheduled → executing → diagnosing → (retrying) → reporting → gated → done` |
| 回环条件 | A5 归因输出 `action_target` 为「测试侧可重试」（数据/用例/环境抖动/竞争残留），且 `attempt < 3` |
| 终态条件 | ① 全部通过；② 归因为 SUT bug（永不重试）；③ 重试 3 次仍失败；④ 归因 `unknown`（不重试，交人工） |
| 回环边界 | **只回环到"执行"节点，不回环到"冲突检测/调度"**——重试不重新分组，保证可重放（对齐 C7.2 的确定性分组） |
| 状态迁移 | 每个状态迁移都写 State，供报告器追溯（谁触发了回环、为什么、第几次） |

> 关键约束：**重试回环是"局部回环"**——只回执行节点，不回冲突检测/调度。因为冲突分组是确定性的，重跑时分组必须不变（可重放），否则失败重跑会对不上原归因。

#### 5.1.2 单用例执行器机制（一个用例怎么跑起来）

每个用例（pytest 函数或独立执行单元）在并发 worker 里走一条固定的执行管道，六个阶段：

```
┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐  ┌───────────┐
│ 1. 造数前置 │→│ 2. Mock注入 │→│ 3. 发请求   │→│ 4. 断言校验 │→│ 5. 熔断监控 │→│ 6. 数据清理 │
│  (setup)  │  │ (拦截下游) │  │  (HTTP/SQL)│  │ (asserts) │  │ (出站扫描) │  │ (teardown) │
└───────────┘  └───────────┘  └───────────┘  └───────────┘  └───────────┘  └───────────┘
```

| 阶段 | 做什么 | 失败时的处理 |
|---|---|---|
| **1. 造数前置** | 按 `data_plan` 的拓扑序执行 setup（外键前置表先造）| 造数失败 → 标记 `data_error`，**不进入请求**，直接归因（可重试：修复造数后重跑）|
| **2. Mock 注入** | 按 `mock_binding` 为下游依赖注册语义响应（见 5.1.3）| 注入失败/未覆盖 → 触发熔断护栏预检，阻断请求 |
| **3. 发请求** | 执行 HTTP 请求（或被测入口调用），记录完整 req/resp | 连接失败 → 归因环境抖动；响应异常 → 进入断言/归因 |
| **4. 断言校验** | 逐条执行 `asserts`（status_code/body_field/…）| 断言失败 → 区分「响应符合契约但值不符=SUT bug」vs「断言本身错=case_error」 |
| **5. 熔断监控** | 扫描本次执行期间是否出现**真实出站请求**（Mock 注入失效）| 检测到透传 → 立即熔断 + 告警，该用例标 `mock_leak`，优先级最高 |
| **6. 数据清理** | 按 `T{case_id}_` 前缀回收本次造的数据（`delete_by_prefix`）| 见下方清理规则 |

> 设计要点：**造数失败不进请求**——这是"数据问题"与"接口问题"的物理隔离。造数挂了直接归因 data_error，不污染接口执行结果，避免"造数失败被误判成接口失败"。

**数据清理规则（第 6 阶段）**：

| 规则 | 说明 |
|---|---|
| **必清，无论成败** | 用例通过/失败/熔断都要执行清理——失败更必须清，否则残留脏数据污染后续用例或重试 |
| **按前缀回收** | 依据 C5 造数设计的 `T{case_id}_` 前缀 + `teardown: delete_by_prefix`，按主键精确删除，不误删他人数据 |
| **重试前先清** | 失败重试时，**重试的第一动作是清理上次残留**，再重新造数——否则"数据已存在"会导致重试永远失败（唯一键冲突） |
| **keep-data 例外** | `--keep-data` 调试模式下跳过清理，保留现场供人工排查（默认关闭） |
| **清理失败告警** | 清理本身失败（如外键级联删除被拒）→ 记录告警，标记 `cleanup_failed`，报告提示可能存在残留，但不阻断门禁（残留不影响本次结论，但需人工关注） |

> 关键：清理不是"可选收尾"，而是**执行管道的固定第 6 阶段**。它保证用例之间的数据隔离——即便一个用例因为 SUT bug 而失败，它造的数据也必须在归因前清掉，否则下一个用例跑在同一张表上会拿到被污染的初始状态，产生连锁假失败。

#### 5.1.3 Mock 编排与熔断护栏（执行期时序）

全 Mock 策略下，Mock 不是"测试前配好就完了"，而是**执行期的一条编排链**。时序如下：

```
用例启动
   │
   ▼
读取 mock_binding（来自 C3.5.1 语义绑定）
   │  {dep_id, branch}
   ▼
查 Mock 语义模板（C3.5 资产）
   │  命中 → 注入该 branch 的编排响应
   │  未命中 → ① 标 semantic_incomplete ② 默认 success + 告警
   ▼
注册出站拦截器（拦截器挂到被测服务的出站通道）
   │
   ▼
执行请求（被测接口内部会调用下游）
   │
   ├─ 下游调用被拦截 → 返回注入的语义响应 ✔
   │
   └─ 出现未拦截的真实出站请求 → 熔断护栏触发 ✘
        │
        ▼
     立即阻断执行 + 告警
     side_effect.has=true 的下游（资损类）→ 熔断优先级最高
     该用例标 mock_leak，不进正常归因
```

**熔断护栏的判定规则**：

| 情形 | 处理 |
|---|---|
| 所有下游都被拦截、无真实出站 | 正常，无动作 |
| 出现真实出站（Mock 注入失效/配置遗漏）| **立即熔断**，阻断本次执行，告警 |
| 熔断涉及 `side_effect.has=true` 下游（资损红线）| 熔断优先级最高，**全批次暂停**，而非只停单用例 |
| 唯一豁免 | Cache/Redis 等随测随建的基础设施，不作为"下游服务"处理 |

> 熔断护栏是全 Mock 策略的**最后防线**。它保证：即便上游（画像/语义绑定）漏识别了某个下游，执行期也不会让真实请求打到生产/第三方（资损风险）。这是"全 Mock"从设计承诺变成运行时保证的关键机制。

#### 5.1.4 与 A5 结果诊断 Agent 的接口

执行编排子图在"归因"节点调用 A5，边界如下：

| 项 | 内容 |
|---|---|
| 触发 | 有失败用例，且确定性归因规则未命中（疑难项）|
| 输入 | 失败用例的 `case + execution + context`（对齐 `prompts/a5_result_diagnosis.md` 的输入契约）|
| 输出 | `root_cause + action_target + confidence + evidence + verify_action` |
| 回环决策 | `action_target` 为测试侧可重试 → 回环执行；`user`/终态 → 进报告 |
| 归因确定性路径 | 大多数失败由**确定性规则**（错误码集合、超时关键词、DB 锁特征）直接归因，**不经过 A5**；只有规则没覆盖的疑难项才兜底给 LLM |

> 关键：A5 的 LLM 只兜底**疑难归因**，不是每个失败都过 LLM。这是"LLM 用量最小化"在 C7 的落地——绝大多数失败（超时、5xx、断言值不符）都是确定性可判的。

## 六、Agent 记忆设计

> Agent 记忆按生命周期分三层，各司其职，避免"什么都往里塞"。AstSight的核心原则：**重资产、轻向量库**——事实源必须是可 diff、可人工编辑的结构化文件，不是 embedding。

### 6.1 三层记忆模型

| 记忆层 | 生命周期 | 存什么 | 载体 | 谁写 / 谁读 |
|---|---|---|---|---|
| **短期记忆** | 单次运行 | 当前流程中间产物与状态 | LangGraph State | 编排器 / 各节点 |
| **长期记忆（资产）** | 跨运行、跨项目 | 可复用的事实源知识 | 版本化资产文件 | **人工维护 / 只读引用** |
| **工作记忆** | 单 Agent 内部 | 该 Agent 多步推理的中间结论 | Agent scratchpad | Agent 自身 / Agent 自身 |

### 6.2 短期记忆 = LangGraph State

编排器在内存中流转的全局状态，运行结束即释放：

```
State：changed_apis / profiles / rules / data_plan / cases / report / 门禁结论
```

- **不落盘**（中间产物另有契约文件承载，见能力文档"能力间落盘通信"）
- 作用是让各节点共享上下文，而非持久化

### 6.3 长期记忆（资产）= 版本化事实源文件

**原则：只读引用 + 人工维护。** 资产是事实源，运行结果不得自动反写污染它，任何更新须过人工审核。

| 资产 | 内容 | 维护方式 | 消费方 |
|---|---|---|---|
| 术语表 | 业务术语/字段语义 | 人工维护，随项目演进 | C3 语义附着、C4 用例设计 |
| 业务规则库 | 字段级业务规则（含 BR 编号、来源、确认状态） | 人工维护（A1 提取 → A1.5 高风险确认/低风险 auto 放行后入库，见 3 章 A1.5） | C3 校验、C4 生成、C5 造数 |
| Mock 语义模板 | 下游依赖的语义分支枚举 | 人工维护 | C3.5.1 语义绑定、C7 执行 |

> 业务规则库的**结构分区**：正式区（`confirmed` + `auto` 放行的规则，供下游消费）+ **deferred 区**（本期不做但保留的规则，供下一轮变更重新评估，见 A1.5 入库规则）。两者同属规则库文件，以 `confirm.status=deferred` 区分，不单独建文件。

**为什么不用向量库**：这三类资产是**结构化、字段级、需精确匹配**的，存成可 diff、可编辑的 JSON/YAML 文件，配合确定性查表即可。向量库适合"语义相似"的模糊召回，但事实源环节最怕模糊——一个字段约束记错就是假绿。

### 6.4 工作记忆 = Agent scratchpad（仅 3 个真 Agent）

仅 A1/A4/A5 需要，用于该 Agent 多步推理时记住"已做了什么、避免重复"：

- **A4 用例设计**：记录"已覆盖哪些规则/接口"，避免重复生成、确保规则覆盖率达标
- **A1 需求分析**：记录"已提取哪些规则条目"，跨文档去重
- **A5 结果诊断**：记录"已尝试哪些归因、重试次数"，避免重试决策反复

S2/S3 能力服务无 scratchpad（纯确定性，无需跨步记忆）。

### 6.5 历史缺陷案例库（框架自我改进资产）

**定位**：保存「框架自身不足导致的用例失败」案例，用于**反向促进框架改进**——它不是给 A5 做归因检索用的，是给框架迭代做依据的。

> 关键区分：普通的"缺陷案例库"记的是"被测系统有什么 bug"；AstSight的"历史缺陷案例库"记的是"**框架自身有什么不足**"。二者是两码事。

**入库判据（只记框架缺陷，不记 SUT 缺陷）**：

| 归因类型 | 是否入库 | 说明 |
|---|---|---|
| SUT 缺陷（真实被测 bug） | ❌ 不入库 | 那是被测系统的问题，交给缺陷追踪 |
| **框架不足**（生成/造数/画像/归因出错） | ✅ 入库 | 如"漏识别下游""约束推错""Mock 语义失真" |
| 环境抖动 / 竞争残留 | ❌ 不入库 | 偶发，非框架缺陷 |

**记录结构**（纯本地文件，`failures/framework_issues.jsonl`，追加式）：

> 一条案例 = 一份"完整失败现场快照 + 根因 + 改进"，信息密度要支撑框架迭代时无需翻原始日志即可定位问题。

```json
{
  "id": "FW-001",
  "category": "case_gen | data_build | profile | mock_semantic | attribution",
  "framework_version": "v2.15",

  "interface": {
    "method": "POST",
    "path": "/api/orders",
    "endpoint_key": "POST /api/orders"
  },

  "params": {
    "request": {"qty": 2, "sku_id": "S001"},
    "response_expect": {"status": 200, "fields": ["order_no"]},
    "response_actual": {"status": 400, "body": {"error": "库存不足"}}
  },

  "downstream_calls": [
    {"id": "pay-gateway", "type": "sync_rest", "mock_semantic": "success"}
  ],

  "biz_context": {
    "rules": ["BR-01 库存校验"],
    "db_tables": ["orders", "products"],
    "constraints": {"qty": "min 1 / max 999"}
  },

  "case": {
    "case_id": "TC-B-012",
    "code": "def test_create_order(): ...",
    "source": "generated | manual"
  },

  "failure": {
    "reason": "case_gen 生成了不存在的业务约束",
    "root_cause": "业务规则库缺失该约束，A4 模板兜底未标记 inferred",
    "llm_initial_judgement": "疑似 A4 生成幻觉：qty 约束与 DB/规则库不符"
  },

  "improvement": {
    "action": "C4 模板兜底时强制标注 inferred，缺失约束须显式告警",
    "category_hint": "case_gen"
  },

  "review": {
    "reviewer": "人工",
    "status": "confirmed | rejected",
    "confirmed_at": "2026-10-20"
  },
  "created_at": "2026-10-20"
}
```

**字段分组说明**：

| 分组 | 字段 | 回答的问题 |
|---|---|---|
| 定位 | id / category / framework_version | 是什么问题、哪个环节、哪个版本 |
| 接口快照 | interface / params | 测的是哪个接口、出入参实际长什么样 |
| 依赖快照 | downstream_calls | 涉及哪些下游、Mock 了什么语义 |
| 业务上下文 | biz_context | 当时的规则、表、约束全貌 |
| 用例资产 | case | 失败的用例代码 + 来源 |
| 失败分析 | failure | 失败原因 + 根因 + **LLM 初判** |
| 改进 | improvement | 怎么改框架 |
| 审核 | review | 人工确认结果（入库前必填） |

### 6.5.1 入库流程（LLM 初判 → 报告 → 人工确认 → 入库）

> 关键：**入库必须过人工确认**。LLM 只做初判，不做终审——避免把 LLM 误判的案例污染进库（一旦污染，框架迭代就会基于错误证据走偏）。

```
用例运行失败（重试耗尽）
        │
        ▼
┌─────────────────────────┐
│ 1. A5 结果诊断           │  归因：SUT 缺陷 / 框架不足 / 环境 / 数据
└───────────┬─────────────┘
            │ 归因 = 框架不足（case_gen/data_build/profile/mock_semantic/attribution）
            ▼
┌─────────────────────────┐
│ 2. LLM 初判（A5 或独立）  │  生成「候选案例」：
│                          │  - 自动收集现场快照（接口/出入参/下游/业务/代码）
│                          │  - 初步判断 root_cause 与 improvement 建议
└───────────┬─────────────┘
            │ 候选案例随报告输出
            ▼
┌─────────────────────────┐
│ 3. 报告呈现给人工         │  候选案例列在报告「框架改进候选」区
│                          │  标注 llm_initial_judgement（明示是 AI 判断）
└───────────┬─────────────┘
            │ 人工确认 / 修正 / 驳回
            ▼
┌─────────────────────────┐
│ 4. 人工确认后入库         │  review.status = confirmed 才写入 jsonl
│                          │  rejected → 丢弃或修正后重提
└─────────────────────────┘
```

**关键设计决策**：

- **LLM 只做初判、不做终审**——它负责"把现场快照收集齐 + 给出初步根因假设"，最终是否入库、root_cause 是否准确，由人工拍板
- **候选案例随报告输出**，不直接写库——报告里单列「框架改进候选」区，人工过目后才落盘
- **`llm_initial_judgement` 与 `review` 分离**——AI 判断永远明示为 AI 判断，人工确认结果单独记录，不混在一起
- **入库判据前置**：只有 A5 归因为「框架不足」才进入候选；SUT 缺陷、环境抖动不进入此流程

**异常与边界**：LLM 初判拿不准 root_cause → 仍生成候选案例，`root_cause` 标 `unknown`，交人工补全；人工长时间不确认 → 候选案例留在报告，不自动入库（宁缺毋滥）

**消费方式（人工驱动，非自动检索）**：

1. 框架迭代时，人工翻阅案例库，提炼共性根因 → 反哺设计/实现
2. 案例库是**促进框架改进的证据来源**，不是运行时检索库
3. 未来若要"按语义相似召回历史案例给 A5 参考"，再评估引入向量库——当前不做

### 6.6 记忆存储与更新总原则

- **存储**：纯本地文件，无独立知识库/数据库
- **资产（长期记忆）**：只读引用 + 人工维护，运行结果不自动反写
- **案例库**：A5 归因为框架不足 → LLM 初判生成候选 → 随报告呈现 → 人工确认后追加；不入库 SUT 缺陷、环境抖动
- **短期/工作记忆**：随运行生命周期释放，不持久化

## 七、关键权衡与风险

| 权衡点 | 决策 | 理由 |
|---|---|---|
| 节点数量 | 3 Agent + 2 能力服务 + 1 编排 | 确定性能力下沉为服务，Agent 只保留会思考的部分 |
| LLM 用量 | 仅 A1/A4 重，A5 弱，S2/S3 零 | LLM 用在"理解/生成"，不用在"计算/追溯" |
| 编排粒度 | LangGraph 确定性骨架 + DeepAgents Agent 本体 | 编排要可预测，Agent 要可思考 |
| 失败策略 | 事实源失败即中止，生成失败可降级 | 上游错了下游全垃圾 |
| 人工介入 | 审核门 + 低置信度确认作为图中节点 | 幻觉防不住，只能人兜底 |

**最大风险**：A4（用例设计）是 LLM 最重、也最容易产出幻觉的环节——它的业务场景联想可能"看似合理实则错误"。对策：① 模板用例打底（确定性）；② 规则匹配打分阈值过滤；③ 代码双重自检；④ 人工审核门硬卡。**四道防线，缺一不可。**

## 八、与能力设计的映射对照

| 能力 | 形态 | LLM 程度 |
|---|---|---|
| C1 文档接入 | A1 需求分析 Agent | 重 |
| C2 变更感知 | S2 变更感知能力服务 | 无 |
| C3 接口画像 | S3 画像构建能力服务 | 无 |
| C3.5 下游依赖控制 | S3 + Mock 编排器工具 | 无 |
| C5 数据准备 | 造数器工具 | 无 |
| C4 用例设计 | A4 用例设计 Agent | 重 |
| C6 用例编码 | A4 + 编码工具 | 中 |
| C7 执行验证 | A5 诊断 Agent + 执行器/报告器工具 | 弱 |

> **能力服务的命名规范**：凡无 LLM 的确定性能力，统一以 `S` 前缀命名（Service），以 `A` 前缀标识真 Agent（含 LLM 自主决策）。避免"画像构建 Agent""变更感知 Agent"这类名不副实的称呼。
