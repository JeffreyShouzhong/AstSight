## 1. 运行环境基线：Linux（2026-10-30）

**决策**：框架的部署与验收环境是 **Linux 服务器 / CI 容器**；Windows 只用于开发机本地调试。

**理由**：

- 实际运行位置是服务器与 CI，容器是主要交付形态；Windows 不是部署目标。
- 路径、子进程、信号、端口绑定、文件锁在两种系统上语义不同；以 Windows 行为为设计前提会在部署时返工。
- Windows 上的测试、spike、CodeGraph 实测都不构成部署验证证据。

**影响**：路径/子进程/信号/端口/锁按 POSIX 语义设计；CodeGraph 原生内核按平台分发，换到 Linux 必须复验；gRPC Mock 选型不看 Windows 可用性。

## 2. 规则层：引入、删除、恢复

**当前口径**：规则库是设计期资产，不作运行时 oracle；v3.0 曾整体删除规则层，v4.0 恢复。

**恢复理由（v4.0）**：业务级用例需要“需求说了什么”的结构化中间物。没有规则层，模型只能从原文直接跳到请求/断言，审核时无法判断“漏了哪条约束”；规则层把需求拆成可逐条核对、可计算覆盖、可 diff 的 BR/CR，用例再逐条挂接。规则只做设计期材料，不做运行时 oracle，因此不会重新引入“规则表达式第二次翻译”的问题。

**约束**：若未来再次删除规则层，必须证明业务级用例的漏检在没有结构化约束清单的情况下仍可被发现。

**时间线**：v2.15 规则库升为一等资产 → v3.0 删除规则层、改用例库（prepare → draft → import → 人工审核 → approve）→ v4.0 恢复规则层并分两级用例。

## 3. Dubbo 下游 Mock：agent + ByteBuddy + Filter（v4.3）

**决策**：SUT → Dubbo 2.7+ 下游的 Mock 用 Java agent 注入、在消费端 `Filter` 拦截，按用例会话返回语义分支；不部署 Mock Provider、不做注册中心替身。

**定位**：从“零侵入”改为**低侵入**——对 SUT 代码/构建零侵入，运行期需加载 agent；调用 SUT 的方向（AstSight → SUT）仍不 Attach、不装 agent。

**落选方案**：

| 方案 | 落选原因 |
|---|---|
| Dubbo 自带 `mock` 属性 | 静态配置，无法按用例切分支 |
| TestableMock | 面向单元测试，不是运行期依赖注入 |
| Byteman | 通用规则引擎，体量过大 |
| jvm-sandbox-repeater | 录制回放，不是会话驱动 |
| ChaosBlade | 只做故障注入，不按语义分支返回 |

**为什么用 Filter 成员关系而不是探针调用判断 agent 是否生效**：Dubbo 在 `refer` 构建 consumer filter 链时才会实例化 `@Activate` Filter，所以 `filter_instantiated` 只有在确实进入调用链时才非 0，不需要发真实调用；而 `No provider available` 发生在 filter 链之前，探针调用也证明不了 Filter 是否进链。

**测试环境边界**：注册中心、provider、SUT 部署由环境保证；`No provider available`、发现超时直接报 `env_error` 并阻断，不伪造 provider、不兜底。

**序列化保真**：Filter 在应用层返回对象，跳过 Hessian2 编解码，报告标 `serialization_verified=false`；需要验证序列化的用例标 `unsupported`。

## 4. gRPC 下游 Mock：gripmock 假服务器 + target 重定向（v4.4 决策，未实现）

**状态**：已决策，未实现；v4.3 报告口径不变（gRPC 下游仍 `mock="unsupported"`）。落地约束见 `framework-capability-design.md` C3.5.4。

### 4.1 问题与约束

SUT → gRPC 下游需要按用例切换语义分支，且不能要求修改 SUT 业务代码。约束按优先级：

1. **运行环境基线是 Linux**（服务器 / CI 容器），Windows 只是开发机；选型不看“能否在 Windows 跑”。
2. **跨语言**：SUT 不一定是 Java，不能只做 JVM 内的拦截。
3. **可重定向优先**：gRPC 的 target 是配置项，能重定向就不进 SUT 进程；只有不可重定向的才考虑 agent。
4. **证据可复核**：必须能回答“这个桩有没有被调用、哪个请求没匹配上”，不能只看响应。
5. **与既有 Mock 会话模型一致**：每命名空间单 active session、mock-bound 用例串行（方案 A）。
6. **不扩大“低侵入”口径**：v4.3 的 agent 只为 Dubbo 存在，gRPC 不因此再装一个 agent。

### 4.2 结论

采用 **gripmock 3.23.6（bavix）** 作为独立 Mock 服务器：每个 Mock 命名空间一个实例，SUT 的 gRPC target 指向它；用例通过 REST stub API 装桩、通过 `/api/history` 取证。原 JVM agent + `ClientInterceptor` 方案降为兜底（target 不可重定向时）。

### 4.3 评估方法

- **环境**：Windows 11 / Python 3.13.14 / grpcio 1.85.0 / protobuf 7.36.2；gripmock 3.23.6；WireMock 3.9.1 + wiremock-grpc-extension 0.11.0（JBR 25）。
- **proto 覆盖点**：嵌套 message、repeated、map、oneof（4 种分支）、`google.protobuf.Timestamp` / `Duration`、int64 大数（`9007199254740993`）、enum、自定义 message 的 `Any` 打包。
- **客户端**：真实 grpcio stub 发 unary，回读并检查 oneof 选择、WKT 的 ISO 形态、int64、enum 名、`Any` 的 `type_url` 与解包、嵌套/repeated/map。
- **判定口径**：只认实测输出，不采信厂商文档或直觉；文档与实测冲突时以实测为准，并把冲突留痕（见 4.6）。

### 4.4 候选与实测

| 候选 | 形态 | 实测结果 | 处置 |
|---|---|---|---|
| **gripmock 3.23.6（bavix）** | Go 单二进制 / Docker；proto 或 protoset 输入；REST stub API；priority；错误状态；history | 复杂响应构造完整：嵌套/repeated/map、oneof、Timestamp、Duration、int64、enum、`Any` 全部正确；未匹配返回 `NOT_FOUND` 且回显完整请求；错误分支细节具体。**请求匹配有真实缺陷：int64 字段无论传字符串还是数字都匹配不上** | **采用**，缺陷由框架侧规避 |
| WireMock 3.9.1 + wiremock-grpc-extension 0.11.0 | JVM jar + descriptor 目录 | 复杂响应同样完整；匹配只认 camelCase；int64 必须带引号；未匹配返回 `UNIMPLEMENTED`，错误细节笼统 | 落选：JVM 依赖、匹配方言更窄、错误分支表达弱 |
| Microcks / Specmatic | 契约 + 示例驱动 | 偏“按契约示例回放”，按示例选响应，不是按用例切语义分支；与本框架会话模型不匹配 | 落选 |
| 各语言 `ClientInterceptor` | 库级拦截 | 每种语言一套实现，且要求改 SUT 依赖/配置 | 落选 |
| 网络 MITM 代理 | 流量改写 | TLS / HTTP2 复杂度高，证据归因困难 | 落选 |
| JVM agent + `ClientInterceptor`（原 v4.4 预留） | 进程内假 `ClientCall` | 技术上可行，但只覆盖 JVM，且要维护 marshaller 往返、`ClassCastException`、`onReady/onHeaders/onMessage/onClose` 时序 | **保留为兜底**：只用于 target 不可重定向（硬编码地址、TLS pinning）且无法改配置的场景 |

#### 双方共同的行为（不构成选型差异，但影响框架设计）

- 非规范形态的 `Timestamp` / `Duration`（对象缺 `seconds`、`nanos` 越界）都被拒绝；
- 未知字段都被拒绝；
- `Any` 未解析/类型缺失都被拒绝；
- **int64 以 number、enum 以 number 都被接受**——服务器不会替框架做严格性，框架必须在发送前校验；
- 未知 method 都返回 `INTERNAL / Exception serializing request!`，而不是 `UNIMPLEMENTED`——不能靠 status 识别“调了没测到的方法”。

### 4.5 落选原因（展开）

- **WireMock**：能力本身够用，落选不是因为功能缺失，而是（a）必须带 JVM；（b）匹配字段名只认 camelCase，和 proto JSON 的 snake_case 习惯冲突；（c）错误分支只能给笼统信息，诊断要再拼一层；（d）在 Linux 上需要额外维护 JVM 版本与堆参数。
- **Microcks / Specmatic**：定位是“契约示例回放/契约测试”，响应由示例决定，不是“同一方法按用例切分支”；要把它们改造成会话驱动，改造成本高于收益。
- **语言级 interceptor**：跨语言不成立，且侵入 SUT 依赖。
- **MITM**：TLS 与 HTTP/2 流复用使证据归因复杂，容易把“没匹配上”误判成“网络问题”。

### 4.6 被推翻的判断

曾判断“gripmock 对复杂嵌套 message、oneof、well-known types 的支持不如 WireMock 稳健”。实测不成立：gripmock 3.23.6 在上述各项上与 WireMock 表现一致，复杂响应同样完整。真正的缺陷是 **int64 请求匹配**，与 WKT/oneof 无关。

留痕目的：避免把厂商宣传、社区印象或直觉当成结论；后续再听到类似判断，先跑同一组 proto 再下结论。

### 4.7 已知缺陷与证据

| 观察到的行为 | 证据（实测） | 框架侧规避 |
|---|---|---|
| int64 请求匹配失效 | 同一请求分别以字符串和数字传 `trace_id`，两种 matcher 都不命中 | 生成桩时不把 int64 放进 matcher；用其余稳定字段（id / 枚举 / 字符串）+ 空 matcher 兜底，命中后框架侧断言 int64 |
| 未知 method 返回 `INTERNAL` | 调 `/spike.v1.SpikeService/NoSuchMethod`，返回 `INTERNAL / Exception serializing request!` | `mock_unexpected_dep` 以 history 的未命中记录 + 框架侧调用清单为准，不看 status |
| int64 / enum 宽松解析 | int64 传 number、enum 传数字均被接受 | 框架发送前做 schema 校验（int64 必须字符串、enum 必须名字），不依赖服务器拒绝 |
| 字段命名双接受 | snake_case 与 camelCase 均能匹配 | 桩只用 proto 字段名生成，字段名契约由框架校验 |
| 未匹配请求回显 | 未命中时 `NOT_FOUND` 带回完整请求体 | 作为 `mock_unexpected_dep` 的定位证据落 run 目录 |

### 4.8 未验证 / 后续复验

- **Linux 目标环境复验**：二进制 / Docker 启动、SIGTERM 停止、端口绑定、`/api/history` 在容器网络下可达；现有结论全部来自 Windows。
- **TLS**：SUT 使用 TLS 连接时，Mock 服务器的证书与 target 改写如何配置，未验证。
- **streaming**：server/client/bidi 未验证；当前设计只承诺 unary。
- **reflection-only**：无 proto/protoset、只开 reflection 的下游，能否建桩未验证；设计上先标 `mock_descriptor_missing`。
- **并发与 history 完整性**：mock-bound 用例串行执行，但同一 Mock 实例被多进程访问时的行为未验证。
- **版本升级回归**：gripmock 升级后必须重跑同一组 proto，尤其确认 int64 匹配是否修复或行为变化。

### 4.9 复现方式

- **被测 proto**：`spike.v1`，`SpikeService` 含 `Unary` / `Echo` / `Ping`；`ComplexRequest/Response` 覆盖嵌套、repeated、map、oneof、Timestamp、Duration、int64、enum、`Any`。
- **客户端**：`call_spike.py --target <host:port> --mode full|echo|unknown|ping`，输出单个 JSON（status/response/checks）。
- **gripmock**：加载 `.protoset`，`POST /api/stubs` 装桩，`GET /api/history` 取证。
- **WireMock**：descriptor 目录 + `/__admin/mappings`，`/__admin/requests` 取证。
- **产物**：spike 目录为临时目录（`%TEMP%\astsight-spike`），不作为仓库资产；需要复跑时按本节重建。

### 4.10 二进制分发：平台专用 wheel（v4.5，2026-11-01）

**问题**：gripmock 是 Go 程序，不能作为 Python 库导入；如何让用户“装完引擎就能用”，而不是自己下载、解压、配置二进制。

**结论**：发布平台专用 wheel `astsight-gripmock-bin`（`linux/amd64`、`linux/arm64`），由 `astsight[grpc-mock]` extra 以精确版本依赖；部署/CI 安装该 extra，容器镜像预装同一 extra。引擎只从包资源目录解析二进制并校验版本与 sha256，不在运行期下载、不查 PATH。

**候选与取舍**：

| 方案 | 用户是否单独下载 | 结论 |
|---|---|---|
| **平台专用 wheel** | 否，随 pip 安装 | **采用**：离线可用、版本可复现、与 CLI 直驱一致；代价是维护架构矩阵与 wheel 体积 |
| 容器镜像内置 | 否 | 采用为交付形态之一：CI/服务器镜像预装 extra，不是唯一形态 |
| 运行期下载 | 首次需要联网 | 落选：离线 CI 不可用、供应链不可控、版本不可复现 |
| Python 重写 gRPC mock server | 否 | 落选：要重做 matcher/history/错误分支，丢掉 4.4 已实测的行为；等于推翻 v4.4 选型 |
| Go 编译为 C shared library + ctypes | 否 | 落选：构建复杂、崩溃隔离差；子进程已满足“每命名空间一实例” |

**关键判断**：

- 用 extra（`astsight[grpc-mock]`）而不是无条件依赖：Windows 开发机与非承诺架构安装基础包不应失败；缺二进制时在运行期显式 `mock_binary_missing`。
- 只承诺 `linux/amd64`、`linux/arm64`：与运行环境基线一致；矩阵外不“尽量试试”。
- 二进制从固定 commit 自建而非直接取上游 release：可复现、可审计；LICENSE/NOTICE 随包。
- `--gripmock-path` 只作开发/应急覆盖，报告 `binary.source=override` 并标 `degraded`，防止生产绕过校验。

**未验证**：manylinux 平台标签与目标发行版的兼容性、arm64 交叉编译产物、单平台 wheel 体积是否触及制品库限制、gripmock 许可证的具体条款。

## 5. 多 SUT 同环境并发隔离（v4.5，2026-11-01）

**问题**：同一个测试环境里同时运行多个 `astsight run`、测试不同 SUT 时，引擎之间会不会互相干扰。

**结论**：进程之间没有共享内存或全局调度器，引擎本身不互相干扰；干扰来自外部资源——端口、文件、命名空间、数据库、用例库。原设计只规定了“单命名空间单 active session”，没有规定端口分配、实例身份和持久化作用域，因此不能承诺隔离。v4.5 补三条硬规则：端口原子分配、实例身份贯穿、持久化按 run 作用域隔离。

**候选与取舍**：

| 方案 | 做法 | 结论 |
|---|---|---|
| 中心注册表 | 引擎启动前向常驻协调服务登记 `sut_id`/端口/命名空间并持有租约 | 落选：引入常驻服务与单点，违背 CLI 直驱、无常驻服务的定位 |
| 文件锁 + 约定命名 | 每个引擎自己 `bind(:0)` 分配端口；`namespace=sut_id`；心跳/运行目录含实例 ID；用例库用 `flock` | **采用**：无中心依赖，失败模式显式（端口占不到、锁冲突），可审计 |
| 共享 Mock 服务按命名空间分区 | 多 SUT 共用一个 Mock 服务，靠会话命名空间隔离 | 不作默认：HTTP Mock 在线上没有命名空间标识，隔离依赖会话副作用；共享服务成为单点。仅当环境已提供共享 Mock 且传输层可分区时允许 |

**关键判断**：

- `bind(:0)` 原子分配优于“端口池扫描”：扫描存在 TOCTOU；“池”本身仍需全局协调。
- 每实例随机 token 必须由引擎生成；全局共享 token 无法阻止一个引擎连到另一个 SUT 的 agent。
- 字面量 `default` 命名空间是共享键，单 SUT 也改用 project 名，避免多 SUT 时静默串话。
- DB fixture 用 `run_scope` 前缀，而不是表级清空：共享库里清整表会删掉其他引擎的数据。
- 用例库写操作用 `flock` 而不是“约定串行”：CI 并发触发 approve 无法靠约定保证。

**被推翻的判断**：“不同进程就天然隔离”。实际隔离取决于每类外部资源是否带实例身份；端口、命名空间、固定心跳路径、DB 键、case store 都会把两个进程连到一起。

**未验证**：Linux 上 `SO_REUSEADDR` 的具体行为、容器网络下 `bind(:0)` 的跨容器可达性、`flock` 在 NFS 上的语义（默认要求本地磁盘或 POSIX 兼容文件系统）。

## 6. Feign 特殊支持：整体删除（v4.6，2026-11-01）

**决策**：设计层面删除对 Feign 的一切特殊支持。Feign 只作为普通 HTTP 客户端：不单独解析 `@FeignClient`、不作契约源、不生成专用配置键、不设专用 `client` 字段或专用 `dep_id` 约定。HTTP 下游统一按通用机制识别与注入；通用机制覆盖不了的下游直接标 `mock="unsupported"` / `unidentified`，依赖它的用例显式排除或 `blocked`。

**理由**：

- 特殊支持的成本不在解析本身，而在它把“HTTP 下游”拆成两条维护路径：契约源优先级、`dep_id` 身份、配置键、Boot 2/3 差异、服务发现覆盖、代理兜底都要各写一份；Feign 的写法差异（继承接口、`contextId` 冲突、SpEL/动态 URL）持续制造边界。
- 通用 HTTP 识别 + 通用注入点已经覆盖同一组能力：调用点、目标地址/端口、可覆盖配置/服务发现/代理。Feign 特例不提供通用机制之外的新能力。
- 明确“覆盖不了就不支持”比维护一条不完整的专用兜底更可审计：失败是显式的 `unsupported`，而不是“以为已经 Mock 了”。
- 引擎仍是 CLI 直驱、无常驻服务的确定性系统；减少按客户端框架分支，符合“事实源环节零猜测”的原则。

**影响**：

- 契约源：HTTP 固定 `OpenAPI > Spring MVC 注解 > 设计文档`；Feign 接口不再作契约源。
- 下游识别：统一识别出站 HTTP 调用点；`dep_id` 初始口径为 `http:{METHOD} {path}`，多调用点追加稳定调用点后缀；无法定位标 `unidentified:<call-site id>`。**该口径已被 v4.6.1 收紧为 `http:{downstream_key} {METHOD} {path_key}`，见 §7**。
- 画像：删除 `client="openfeign"`、`接口简单名#方法名` 的 id 约定与 Feign 专用 `contract_source` 取值；`mock.strategy` 初始收敛为 `url_override | discovery_override | proxy_fallback | unsupported`，**v4.6.1 将 `proxy_fallback` 明确为仅明文的 `http_proxy`**。
- Mock 注入：只保留通用配置 URL 覆盖、服务发现覆盖、出站代理；不生成任何客户端框架专用配置键；覆盖不了即 `unsupported`。
- 用例与门禁：`mock_bindings` 类型为 `http/dubbo`；HTTP 下游必须给出 `mock.strategy` 与实际配置键（或代理/发现覆盖证据）；`unsupported` 下游必须显式声明且依赖用例 `blocked`。
- 里程碑 M2.4 由“OpenFeign 接入”改为“HTTP 下游通用接入”。

**被推翻/收紧的判断**：

- 推翻 v4.1 “优先支持 OpenFeign、`client="openfeign"`” 与 v4.2 “Feign URL 覆盖 + 专用配置键”的专项设计。
- 推翻“无 OpenAPI 的 Feign 项目靠 Feign 接口作契约源”的思路：这类项目改走 Spring MVC 注解或设计文档；仍不可得则 `contract_incomplete`。
- 保留原则不变：HTTP 客户端仍是消费方，不是端点；Mock 必须在 HTTP 边界完成，不得在同一 JVM 内 mock 客户端 bean。

**未验证**：不同 HTTP 栈（HTTP/2、连接池、自定义传输实现）与代理覆盖的实际兼容性，需按真实 SUT 做 spike。这是通用 HTTP 机制的风险，不是 Feign 特有的；覆盖不了时按 `unsupported` 处理，不做专用兜底。

**历史条目**：v4.1/v4.2 中与 Feign 相关的决策保留在版本变更记录中，标注为已被 v4.6 取代。

## 7. HTTP 下游 Mock：仅明文 + dep_id 唯一性 + v1 支持边界（v4.6.1，2026-11-02）

**决策**：

1. **首版只支持明文 HTTP**。HTTPS 下游不做协议降级、不做 MITM、不安装测试 CA；统一 `mock="unsupported"`、`unsupported_reason="tls_not_supported"`，依赖它的用例 `blocked`，报告单列。
2. **`dep_id` 改为携带下游身份**：`http:{downstream_key} {METHOD} {path_key}`。`downstream_key` 按 `svc:`（逻辑服务名）> `cfg:`（base URL 配置键）> `host:`（解析后的主机，回环地址带端口）> `call:`（调用点）取值；`path_key` 归一化占位符、去掉 query、合并斜杠。同一下游端点的多个调用点**合并**为一个 dep；不同目标归一后仍撞 id 时降级 `downstream_key` 并追加目标哈希，仍冲突则 `dep_collision` 阻断。
3. **`dep_id` 不按用例区分**：`dep_id` 跨用例稳定，用例级差异由 `mock_bindings[].branch` 表达；`route_key` 只由 `dep_id` 生成，SUT 启动时注入一次。把 `case_id` 编进 `dep_id` 会迫使同一 SUT 进程按用例改 URL 配置，并把同一端点拆成多个身份，导致画像/覆盖率/证据碎片化。
4. **运行期用 `route_key` 路由**：`route_key = "r" + sha256(dep_id)[:12]`，注入 URL 为 `http://<mock>/_dep/<route_key>`；另支持 `Host` 路由（服务发现）与唯一 `METHOD+path` 兜底。未知 `mock_route_unknown`、歧义 `mock_route_ambiguous`，绝不透传、绝不默认 200。
5. **HTTP Mock 内嵌在引擎进程**：FastAPI/uvicorn，每 `sut_id` 一实例，`bind(127.0.0.1:0)` 端口写 run manifest；admin token 每实例随机；会话复用 C3.5 的 `POST/DELETE /_admin/sessions`。
6. **首版支持边界按“承诺 / 条件支持 / 不支持”三档落定**：C3 按 `url_override`（专用配置）> `discovery_override`（仅环境支持时）> `http_proxy`（显式）> `unsupported` 选择；一个 dep 只选一种策略，运行期不自动降级、不改选。选不出即 `unsupported`，依赖用例 `blocked`。

**v1 支持矩阵**：

| 能力 | v1 状态 | 条件/说明 |
|---|---|---|
| `url_override`（专用配置） | **承诺** | 配置键只服务一个 dep：一个下游专属 base URL，或一个完整 endpoint URL |
| `url_override`（共享 base URL） | **不支持** | 一个配置键服务多个 dep 时无法注入多个 `route_key`；应转 `http_proxy`，否则 `unsupported`（`mock_config_ambiguous`），不猜测 |
| `discovery_override` | **条件支持** | 仅当测试环境提供可重定向的注册中心或静态服务列表；否则 `discovery_not_supported`，不计入 v1 承诺 |
| `http_proxy`（显式代理） | **承诺** | 仅明文 HTTP；客户端必须遵循 `HTTP_PROXY` / `-Dhttp.proxyHost` 等显式代理配置 |
| `http_proxy`（透明代理） | **条件支持** | 需要环境提供 iptables REDIRECT 与权限；框架只输出规则，不作为 v1 承诺 |
| HTTPS | **不支持** | `tls_not_supported`，不降级、不 MITM |
| 同 JVM 内 mock HTTP 客户端 bean | **不支持** | 绕过编解码/拦截器/降级链，测不到真实调用路径 |
| 动态 URL / 自定义传输 | **不支持** | 除非可经明文代理覆盖；否则 `unsupported` |
| 请求匹配、调用序列、h2c、WebSocket、流式 | **不支持** | v1 明确边界 |

**理由**：

- 原 `http:{METHOD} {path}` 不含下游身份。两个服务都暴露 `GET /api/v1/status` 时，URL 覆盖后它们命中同一个 Mock 主机、同一个 Host、同一个 method+path，Mock 无法区分；`dep_id` 重复，用例绑定会串。
- 用例级差异应由会话分支表达，而不是身份。`route_key` 在 SUT 启动时注入，运行期不能按用例换 URL；若把 `case_id` 编进 `dep_id`，同一端点会被拆成多个身份，同一套 SUT 配置也无法同时服务这些身份。
- 用调用点后缀消歧又会走向另一个重复：同一下游端点被两个调用点调用时被拆成两个 dep，用例要绑两次，运行期却仍无法区分调用点。正确做法是“按下游端点合并、按下游身份区分”。
- 先做明文 HTTP 能覆盖大多数内部服务，同时避开 TLS 信任链、证书分发、pinning、mTLS 这一整类环境依赖；HTTPS 支持应作为独立决策，而不是在首版里悄悄降级。
- `route_key` 把“可读身份”和“URL 安全”分开：`dep_id` 可读、稳定，URL 只带短哈希；网关重写路径也不影响前缀路由。
- 共享 base URL 无法用 `url_override` 表达多个 dep 的注入：一个配置键只能填一个 URL，塞进多个 `route_key` 必然有一部分下游被路由到错误分支。与其猜“哪个 dep 该用哪个 key”，不如显式 `mock_config_ambiguous` 并转代理。
- `discovery_override` 依赖注册中心/服务列表可写，属于环境能力而不是框架能力；把它列为“条件支持”可以避免在无法重定向的环境里承诺做不到的覆盖。显式 `http_proxy` 是唯一不依赖 SUT 配置面的承诺路径。
- 首版不承诺同 JVM bean mock、动态 URL、请求匹配、序列和流式：这些要么绕过真实调用链，要么需要框架接管请求语义，都会把“Mock 下游”变成“重写 SUT 行为”。

**落选方案**：

| 方案 | 落选原因 |
|---|---|
| 保留 `http:{METHOD} {path}` + 调用点后缀 | 同路径跨服务仍撞；同端点多调用点被拆成多个 dep；运行期无法区分调用点 |
| `http:{host}:{port} {METHOD} {path}` | 环境相关，域名/端口变化导致 `dep_id` churn；服务名/配置键更稳定 |
| `dep:<hash>` 纯哈希 | 不可读，审核与排障成本高；哈希只适合做 `route_key` |
| HTTPS 降级为 HTTP | 客户端/网关可能拒绝，测到的不是真实链路；静默降级不可审计 |
| MITM + 测试 CA | 需要改 SUT truststore；pinning/mTLS 下不可行；首版不引入 |
| 用共享 base URL + 路径前缀区分多个 dep | 一个配置键只能注入一个 `route_key`；其余下游会被错误路由，且无法在运行期按 dep 切换配置 |
| 将 `discovery_override` 列为无条件承诺 | 注册中心/静态列表不可重定向时必须报 `discovery_not_supported`；承诺后无法兑现，只会把限制推到运行期 |
| 用 JVM bean mock / 动态 URL 重写兜底 | 绕过真实编解码、拦截器与降级链，测到的不是生产调用路径 |

**影响**：C3 步骤 6、Profile 示例、C3.5 注入矩阵与 v1 支持矩阵、C3.5.1 语义模板、新增 C3.5.5、失败子码（`mock_config_ambiguous`/`discovery_not_supported`）、数据模型（`MockServer`/`MockRoute`/`MockCall`）、5.5 实例归属、门禁、风险、M2.4/M2.13/M4、`prompts/a4_case_design.md`。

**未验证（落地前 spike）**：

- Java/Python/Go 主流 HTTP 客户端对 `HTTP_PROXY`/`-Dhttp.proxyHost` 的遵循程度；
- 透明代理在容器内的 iptables 权限与可用性；
- uvicorn 下 `drop_connection` 能否真正 reset，还是只能退化为延迟超时；
- 不同注册中心的“服务名 → Mock 地址”覆盖方式；
- 客户端拼接 base URL 时是否会 URL-encode 或规范化 `/_dep/<route_key>` 前缀。

**边界**：不做请求匹配、不做调用序列、不做 HTTPS/MITM、不做 h2c/WebSocket/流式、不做动态 URL 重写；同一下游端点的多个调用点共享分支，需要按调用点区分时标 `mock_binding_ambiguous`，不拆 `dep_id`。

## 9. 规则驱动 A4 与 C5a/C5b 拆分（v4.7，2026-11-02）

**背景**：设计文档已把规则库恢复为一等资产（v4.0），但实现仍保留“需求 → 语义分析 → 用例草案”的旧链路，A4 绕过规则层直接让模型生成请求/断言；C5 同时被描述为“A4 的输入”和“按已批准用例输出”，形成循环依赖。本节记录对齐时的取舍。

**决策一：A4 只消费结构化资产，不消费原始需求**。A4 的输入是 `ruleset.json`、`context`、`profiles`、`mock_semantics.json`、`data_catalog.json`；模型负责把“规则 + 接口画像 + 可用造数能力”组合成用例草案，不再先做一轮自由语义分析。理由：规则已经承担“需求说了什么”的结构化职责，再保留一层语义分析会让同一事实出现两个来源，审核时无法判断用例漏的是规则还是分析结论。`agent/semantic.py` 的用例生成职责因此移除；C3.5.1 的下游分支语义保留在 `mock/semantic.py`。

**决策二：C5 拆成两个时点**。C5a 在 A4 之前产出 `data_catalog.json`，回答“有哪些表/列/外键/枚举/可复用业务态”；C5b 在人工批准之后产出 `data_plan.json`，回答“这条已批准用例怎么造数、怎么回收”。理由：A4 需要知道可选前置状态，否则会生成无法造数的 `preconditions`；而逐用例造数计划必须绑定已批准的 `case_id`，不能反过来作为 A4 的输入。拆分后 `DataCatalog` 是 A4 输入，`DataPlan` 只被 C6/C7 消费。

**决策三：C5 使用大模型，但只做语义候选**。字段业务含义、业务态候选、枚举取值解释由 LLM 基于 DDL + profiles + 规则/需求原文提出；DDL 解析、外键闭包、拓扑排序、类型/枚举/非空校验、参数化 SQL 渲染、SQLite apply/teardown 与事务回滚全部确定性。理由：仅靠列名/类型推断业务语义不可靠（如 `status` 的取值含义、`deleted_at` 与软删除状态的关系），但让模型直接产出 SQL 会把注入面、方言差异和不可复现性带进执行链路。无原文依据的语义标 `inferred`，无法定位标 `unmapped`，不得标 `verified`。

**决策四：诚实降级优先于跑通**。v1 只实现 SQLite 造数；其他方言标 `unsupported_dialect`。带 `preconditions` 的用例在没有 `data_plan.json` 或没有 `ASTSIGHT_DB_URL` 时标 `blocked`/`data_unavailable`，不静默跳过、不伪造通过；没有前置状态的用例行为不变。A6 自修复保留为可选扩展，只允许修改 `path_params/query/headers/body/asserts`，不得改用例身份、规则引用、前置状态或 Mock 绑定，且必须重新走 proposal/approve。

**影响**：`caseset` schema 升到 2、fingerprint 升到 2；旧 store 直接报 `store_schema_unsupported`，不静默迁移。`testcases.json` 统一为已批准用例的运行投影 `cases.json`。A4 断言值字段统一为 `expect`，`mock_bindings` 统一为 `dict[dep_id, branch]`，HTTP 端点统一为 `METHOD /path`。

## 10. 规则阶段取消人工审核（v4.8，2026-11-03）

**背景**：v4.0 恢复规则层后，规则本身没有独立审批命令，但“未裁决冲突 → `disputed` → 用例不能批准 → `rules resolve`”事实上又造出一个人工节点。规则阶段（A1 抽取 → 导入校验）本身已是确定性的，人工在这里既不改变模型输出，也不决定执行口径，只是把同一个判断提前做一遍。

**决策一：规则阶段不设人工门禁**。`rules import` 校验通过即原子落库；不引入规则 proposal/approve，也不再提供 `rules resolve`。全流程唯一的人工审核节点是用例审核（import → 审核文件 → approve），规则在被 approved 用例引用后才算确认。

**决策二：冲突只记录、不改变规则状态**。框架确定性检测与模型自报的冲突都保留在 `ruleset.conflicts`（`origin` 区分来源），参与冲突的规则仍为 `active`，可被 A4 引用。冲突进入 A4 输入和用例审核文件；A4 不得自行裁决或改写规则值，引用冲突规则的用例带 `rule.conflict` warning；执行报告把冲突列为待确认项，不阻断。

**理由**：冲突是否需要取舍，最终取决于“哪条规则变成用例的 oracle”，这正好是用例审核要做的决定。把裁决放在规则阶段会让审核人先看一遍规则、再在用例里看一遍同样的事实，节点翻倍而信息不增。保留冲突记录与审核展示，等价信息仍在，只是合并到唯一的人工节点。

**风险与边界**：模型可能基于互相矛盾的规则各生成一条用例。这不是静默错误——审核文件逐条列出冲突 topic、规则编号与来源，相关用例带 warning；审核人可以拒绝、修改或只批准一方。规则值落地校验（quote 逐字核对）仍由框架确定性执行，不依赖人工。

**影响**：删除 `RuleStatus.disputed`、`rules resolve` 命令与 `RuleConflict` 的人工裁决字段；`ruleset` schema 升到 2，旧库直接报 `ruleset_schema_unsupported`，不静默迁移；`rules status` 输出 `conflict_count`，`RuleSet.conflicts` 保留 `topic/rule_keys/docs/origin/reason`。

## 11. 规则评审文档与重抽闭环（v4.9，2026-11-03）

**背景**：v4.8 取消了规则阶段的人工审核，但“规则抽得对不对、需求哪里写不清楚”仍需一个可交付物去和产品方沟通。若只把 JSON 规则库丢给产品，冲突、缺口和待确认问题会被淹没；若让人工直接改规则库，又会多出第二个真相源，且无法解释下一次抽取为什么和手工修改不一致。另一个实际问题是：需求修复后重新抽取，上一版的问题如何消失。

**决策一：A1 按“能不能只靠文档内部判定”四分流**。`rules` 是文档明确且可判定的约束，框架直接消费；`conflicts` 是文档内部可判定的矛盾（词义与行为冲突、两处口径不一致、取值/阈值矛盾、枚举未闭合、分支不可达、双向效应、自反触发），当场成立、不需要人回答；`gaps` 是文档没写的内容，回写需求；`questions` 是必须由业务决策或外部事实回答的问题。内部可判的矛盾不得降级为 `questions`——降级会把一个已经成立的缺陷变成一条等排期的问题，往往等不到答案；需要人回答的问题也不得冒充 `conflicts`，否则会被误认为文档已经自己暴露了。

**决策二：评审文档由代码渲染，不是模型第二份输出**。`rules render` 从 `ruleset.json` 生成 `ruleset.md`（规则表 / 冲突 / 定义缺口 / 隐含假设 / 业务确认清单 / 枚举未闭合项），`rules import` 与 `agent run` 在写库后自动产出同目录的 `ruleset.md`。这份文档是只读视图：条目、编号、数字都来自同一份 JSON，版式变化不需要重跑模型；它只用于和产品方对齐需求缺陷，不是审批节点，也不参与导入。若让模型同时输出 JSON 和 Markdown，两次生成的条目数会对不上，且没人能判断哪份可信。

**决策三：重新抽取是完整快照，旧问题不能残留**。每次 `rules import` 都以本次草案为准整体替换 `questions/gaps` 与 `conflicts`；上一版存在、本次不再检出的冲突（无论模型自报还是框架检测）直接消失。这样“回写需求 → 重新 prepare/import → 再看评审文档”才能收敛：如果旧冲突永久保留，修复完成后文档上仍显示同一个缺陷，没人能判断这次修复是否生效。代价是模型重跑的不确定性可能让某个冲突这次没被检出；这与“完整抽取”的口径一致，由评审文档和用例审核兜底，而不是靠永久累积旧结论。

**决策四：规则库不接受手工修改**。`ruleset.json` 只能由 `rules import` 写入，不提供编辑命令；`ruleset.md` 是只读产物，改它不会影响规则库。要改规则，只能改需求原文后重新抽取。通过确定性校验（quote 逐字落地、A 级降级、枚举 `exhaustive` 声明、冲突记录）的规则即可直接被 A4 用于生成用例，不需要再等一次规则确认；规则最终被 approved 用例引用后成为“已确认规则”。

**风险与边界**：评审文档只覆盖文本层可测性（可判定性、一致性、部分可观测性与完备性），发现不了整段缺失的功能、业务上写得很清楚但错误的规则，也不覆盖可控制性/可隔离性；这些边界在提示词与文档中显式声明，不用“覆盖率达标”之类结论掩盖。重抽后 `rule_key` 随文本变化，引用旧规则的用例表现为 `stale`/orphaned，这是需求变更的正常结果，不是数据损坏。

**影响**：`RuleDraft`/`RuleSet` 增加 `conflicts.kind/severity`、`gaps.check_dimension/affected_rule_keys`、`questions.source/related_rule_keys`（均有默认值，schema 2 不变）；`RuleConflict.kind` 决定处置路径，`severity` 只用于排序；`rules import` 输出新增 `review` 路径。

## 12. OpenAPI 不再作为流程前置条件（v4.10，2026-11-03）

**背景**：代码把 OpenAPI 当成“契约是必需事实源”，`cases prepare` 和 `agent run` 在没有契约文件时直接失败。但真实开发阶段通常没有可交付的 OpenAPI：它要么由框架在运行时生成，要么根本没人维护。需求阶段的输出是业务规则，本来只需要文档原文；接口的 method/path/handler 可以从代码路由得到，字段约束有则更好、没有也不该让整条链路停摆。

**决策一：需求→规则不碰 OpenAPI**。A1 的输入仍是需求/设计文档；OpenAPI 只用于补充 CR 契约规则。缺少契约时 `ruleset.contract_rules` 为空，这是显式结果，不是失败。

**决策二：接口事实分两级**。C3 先用路由插件/CodeGraph 得到 method+path+handler 与下游调用点；OpenAPI 存在时再补 `params/request_body/body_required/response_fields/error_codes`。缺契约的画像标 `contract_incomplete=true`、`contract_incomplete_reason=openapi_missing`，每个接口都可见，而不是让整条流程报一个笼统的“没有 OpenAPI”。

**决策三：缺失不等于否定**。用例校验不能因为 `params`/`request_body` 为空就判定“字段未声明”。`contract_incomplete=true` 时跳过 query/header/body 字段白名单，只保留路径占位符、断言结构与 quote 落地等确定性检查；A4 只能使用需求原文或规则中明确出现的字段名，无法确定就跳过并写入 `uncovered_requirements`。有 OpenAPI、但某个 operation 缺失时仍逐接口记 `openapi_operation_missing`——这是“契约说没有”，与“契约未知”必须区分。

**决策四：没有接口时先完成规则，再明确收尾**。`agent run` 扫不到任何可用路由时不再在入口处抛 `no_routes`：它继续完成 A1 规则抽取、写出 `ruleset.json`/`ruleset.md`，然后以 `not_run` 结束并给出 `routes_missing`。规则是需求阶段的有效产物，用例没有接口事实则无法诚实生成；用一条“只会打 200”的假用例盖住缺口，比不生成更糟。

**风险与边界**：代码路由只证明“接口存在”，不证明字段类型、必填、枚举或错误码；由代码反推的字段约束只能作为契约回归线索，不能当业务正确性的 oracle。没有 OpenAPI 时字段格式类、必填类用例会减少，报告必须把 `contract_incomplete` 与缺失的 CR 规则单列，不能用“覆盖率达标”掩盖。

**影响**：`context.json` 新增 `warnings`、`interface_evidence`，`context_id` 纳入路由投影 hash（接口变化会让上下文过期）；`profile` 新增 `contract_incomplete_reason`、默认 `error_codes=[]`；`cases prepare` 新增 `--no-scan-routes` 与 `--codegraph`；A4 画像视图改为 `params/request_body/body_required/contract_incomplete`；`validate_draft` 在 `contract_incomplete` 时不再把请求字段判为未知。

## 13. 需求文档是规则抽取的唯一入口（v4.11，2026-11-03）

**背景**：规则抽取在实现上被拆成 `rules prepare`（确定性上下文）与 `rules import`（校验写库）两条命令，文档也把它们写成了用户步骤。但用户面对的是需求文档，不是中间文件：一次抽取应该由需求文档直接产出规则库和评审文档；重抽的入口同样应该是修改后的需求文档。`prepare`/`import` 是框架内部的两段边界，不是产品概念。

**决策一：`rules extract` 是入口**。它按顺序执行：`build_rules_context` → `write_rules_context`（context/prompt/schema/README）→ 适配层模型产出 `rules.draft.json` → 框架校验/降级/冲突检测/CR 合并/diff/版本化 → 原子写 `ruleset.json` + 渲染 `ruleset.md`。`--dry-run` 只校验不写库。模型输出先落盘再校验：校验失败时规则库保持原样，但草案保留，便于区分“模型抽错”和“需求本身不可判定”。

**决策二：`prepare`/`import` 保留为两段式管线**。当模型不能在框架进程内运行时（Claude Code Skill、人工在 ChatGPT/Claude 中生成、企业模型网关、离线批处理、无法出网的环境），用 `rules prepare` 只产出上下文包，外部执行者写 `rules.draft.json`，再由 `rules import` 完成**完全相同**的确定性校验与写库。两条路径不产生第二套规则口径：`rule_key`、A 级落地、冲突检测、CR、diff、版本号都由同一份代码计算。

**决策三：模型在两种模式下都不是写入者**。无论 `extract` 还是 `import`，模型只提交 `RuleDraft` 候选；`ruleset.json` 只能由框架写。这是“规则库不接受手工修改”的延伸：模型和人都不能绕过校验直接改规则库。

**影响**：CLI 新增 `rules extract [--requirements ...] [--openapi ...] [--rule-base ...] [--out ...] [--max-rules ...] [--prompt ...] [--dry-run] [--json]`；`rules prepare`/`rules import` 的帮助文本改为“框架外模型的两段式”；README 与设计文档的 canonical 链路改为从需求文档进入 `rules extract`。

## 14. C5 造数方言扩展到 PostgreSQL/MySQL（2026-11-12）

**背景**：v1 只实现 SQLite 造数，MySQL/PostgreSQL 显式 `unsupported_dialect`。真实服务多数使用 MySQL 或 PostgreSQL，如果造数只能跑 SQLite，带数据库前置状态的用例在真实项目上会全部 `blocked`，C5 等于不可用。

**决策一：方言在计划生成时固化，执行时不改写 SQL**。`data_plan.json` 记录 `dialect`；SQL 占位符与标识符引用在 `render.py` 按方言生成（SQLite `?`/双引号、MySQL `%s`/反引号、PostgreSQL `%s`/双引号）。执行前校验计划方言与 `--db-url` 一致，不一致直接 `dialect_mismatch`，避免把 `?` 发到 PostgreSQL/MySQL 后靠驱动猜测。

**决策二：驱动按需导入，缺驱动显式失败**。SQLite 用 stdlib；PostgreSQL 用 `psycopg`，MySQL 用 `PyMySQL`。运行时导入失败报 `db_driver_missing`，不降级成“无造数”。两个驱动加入 `requirements.txt`。

**决策三：事务语义与校验口径不随方言变化**。fixtures 的表/列/类型/枚举/FK 校验完全一致；整批 statement 在一个事务内执行，失败回滚；teardown 按主键逆序删除。方言只影响连接、占位符与标识符引用。

**边界**：不做建库/迁移/连接池/跨库事务；PostgreSQL schema 限定名、MySQL 特殊类型（如 `BIT`、空间类型）与方言特有默认值仍按通用规则处理，遇到即由校验或数据库拒绝，不猜。

**影响**：新增 `data/dialects.py`；`DataPlan` 增加 `dialect`；`data catalog --dialect`、`agent run --db-dialect`；生成物 `conftest.py` 的 `data_state` 支持三种驱动；新增 `test_data_dialects.py`。旧计划缺少 `dialect` 时按 SQLite 处理，与旧行为一致。

## 15. A5/A6 合并、运行期自动修复与 Mock 结构失配（v4.13，2026-11-12）

**背景**：原来的失败处理拆成 A5（归因）与 A6（修复）两个 LLM 节点，两次请求容易互相矛盾；A6 默认关闭且修复结果仍需人工批准，实际运行中几乎不会生效。另一方面，真实失败里很常见的一类是：**Mock 返回的结构不符合 SUT 代码读取的字段，或不符合业务事实**（例如代码读 `unit_price_cents`，Mock 给的是 `price`）。这类失败在 SUT 侧表现为 5xx/KeyError，如果只按“SUT 缺陷”处理就会误判，也无法自愈。

**决策一：A5 与 A6 合并为同一节点**。一次模型调用同时输出 `diagnoses[]`（归因）与可选 `patch`（用例补丁、Mock 分支补丁）。`RepairPlan.schema_version=2`；提示词统一为 `prompts/a5_diagnose_repair.md`，旧的 A5/A6 提示词保留为废弃指针。归因仍需引用证据，补丁必须能说明“为什么这样改能修复该失败”。

**决策二：默认最多 3 轮、0 关闭**。`FlowConfig.max_repair_rounds=3`，CLI `--max-repair-rounds` 默认 3、上限 5。每轮：应用补丁 → 重跑 → 再次诊断；无补丁或补丁被拒即停止。重跑使用 `<run_id>-repairN` 独立目录，保留每轮 `repair-N.*` 快照。

**决策三：运行期修复是 Agent 动作，不伪装人工审核**。初始用例入库仍必须人工 `cases approve`；修复阶段的用例补丁走同一套 proposal/diff/校验，但由固定身份 `astsight-agent:repair` 自动批准 `new/update/revive`，`deprecate` 一律拒绝。`review_log` 记录该身份，报告中可追溯，不声称“已人工审核”。

**决策四：断言护栏是硬约束**。补丁修改 `asserts` 时，若断言条数减少，或按内容推导的强度（L1–L4）下降，整条补丁拒绝并记录原因。补丁不得修改 `case_key/level/rule_refs/requirement_refs/preconditions` 等身份字段；违法即拒绝，不做部分应用。

**决策五：Mock 结构失配按 `mock_error` 修复**。可修的 Mock 范围仅限该用例**当前绑定**的分支（`mock_bindings` 中 `dep_id -> branch`），可改 `status/headers/body/semantics`，也可改用例绑定的分支。5xx 只有在归因为 `mock_error` 且用例存在 Mock 绑定时才进入可修集合；否则按真实缺陷或未知处理，避免把代码 bug“修绿”。修复写回 `.astsight/mock_semantics.json` 并调用 `sync_mock_semantic` 热替换运行中 Mock 路由表的 stub，无需重启服务。

**边界**：数据错误、环境抖动、真实 SUT 缺陷不触发修复；正向用例的超时类失败不修；修复不新增用例、不提升覆盖；模型补丁按不可信输入校验，失败回滚到应用前状态。

**影响**：`agent/models.py` 新增 `MockBranchPatch`/`RepairDecision`，`RepairPlan` 升到 v2；`agent/diagnosis.py` 只保留载荷与可修性判断；`agent/repair.py` 提供 `diagnose_and_repair`；`agent/mockplan.py` 新增 `sync_mock_semantic`；`agent/flow.py` 改为单节点 + 3 轮循环；运行产物新增 `diagnosis.json`、`diagnosis_meta.json`、`repair.json`、`repair-N.*`。
